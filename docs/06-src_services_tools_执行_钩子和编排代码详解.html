Claude Code Source Analysis

src/services/tools 四个 TypeScript 脚本详细解析

本文针对 BennettBin/Claude-code 恢复源码中的 src/services/tools 目录， 逐个分析 StreamingToolExecutor.ts、toolExecution.ts、 toolHooks.ts 和 toolOrchestration.ts。 重点不是逐行翻译，而是解释每个脚本的整体结构、主要类/函数、内部调用关系、 脚本之间如何协作，以及它们在整个 Claude Code Agent/Tool Runtime 中承担什么系统职责。

一句话总览： 这四个文件共同组成 Claude Code Tool Runtime 的核心执行层： toolExecution.ts 是“单次 Tool Call 执行内核”， toolHooks.ts 是“Hook/Permission 适配层”， toolOrchestration.ts 是“非流式批量调度器”， StreamingToolExecutor.ts 是“流式、有状态的并发调度器”。

说明：BennettBin/Claude-code 不是 Anthropic 官方开源仓库，而是根据公开发布物/source map 恢复出的源码树。 本文描述的是该恢复源码中可以直接观察到的实现结构。

1. toolExecution.ts

单次 Tool Call 执行内核

1.1 脚本的核心作用

toolExecution.ts 是四个文件中最核心、体量最大的一层。 它并不负责决定多个 Tool 之间“谁先谁后”，而是负责回答： 给我一个已经由模型产生的 tool_use，如何把它安全、可观测、可恢复地执行成一个 tool_result？

从职责上看，它把一个 Tool Call 拆成完整的执行 pipeline：

tool_use
   ↓
Tool lookup / alias fallback
   ↓
MCP metadata 识别
   ↓
Abort 检查
   ↓
Zod Schema Validation
   ↓
Tool-specific validateInput()
   ↓
Input preprocessing / backfill
   ↓
PreToolUse Hooks
   ↓
Hook Permission + Rule Permission + User Permission
   ↓
tool.call()
   ↓
Progress forwarding
   ↓
Result mapping / telemetry / tracing
   ↓
PostToolUse Hooks
   ↓
tool_result / Attachment / contextModifier

异常路径：
tool.call() exception
   ↓
错误分类 / MCP auth state 更新
   ↓
PostToolUseFailure Hooks
   ↓
error tool_result

1.2 整体结构

大致区域结构作用
文件头大量 imports连接 Tool abstraction、权限系统、Hooks、MCP、Analytics、OTel tracing、消息封装、ToolSearch 等。
前部 helperclassifyToolError() 等处理 telemetry-safe 错误分类、权限来源映射、MCP server metadata、图片 ID 等辅助逻辑。
主入口runToolUse()接收单个 ToolUseBlock，处理 Tool 查找、未知 Tool、取消，并把执行委托给下一层。
流式桥接streamedCheckPermissionsAndCallTool()把 progress callback + 最终结果统一包装成 AsyncIterable，供上层 scheduler 流式消费。
Schema HintbuildSchemaNotSentHint()当 deferred tool schema 没被送到模型、导致参数类型错误时，提示模型先通过 ToolSearch 加载工具。
执行主体checkPermissionsAndCallTool()完成 Schema、validateInput、PreHook、Permission、实际调用、PostHook、结果/异常处理。

1.3 主要函数解析

A. classifyToolError(error)

这个函数用于把真实异常转换成适合 telemetry 记录、又不会意外泄露敏感路径或内容的错误类别。 它优先使用专门的 TelemetrySafeError 信息；文件系统错误倾向记录 ENOENT、 EACCES 等 errno code；已知 Error 可使用稳定的 error name；无法安全确认时退回通用错误类型。

系统意义：这是 Tool Runtime 的 observability 防线。Tool 执行错误可以统计，但日志不能直接把用户代码、文件路径或命令全部当错误标签上报。

B. Permission source helpers

ruleSourceToOTelSource() 与 decisionReasonToOTelSource() 把各种内部 permission 来源统一映射为 telemetry 中稳定的来源 vocabulary。 例如 session 级允许、持久设置允许、hook、classifier、config 等。

系统意义：权限不是简单 true/false。系统还需要回答“为什么允许/拒绝”，用于安全审计和行为分析。

C. MCP helper functions

  • findMcpServerConnection()：根据 mcp__... Tool 名称反查 MCP Server Connection。
  • getMcpServerType()：识别 stdio / sse / http / ws / sdk 等 transport 类型。
  • getMcpServerBaseUrlFromToolName()：获取适合日志记录的 MCP endpoint metadata。

系统意义：MCP Tool 最终仍然进入统一 Tool Runtime，但 Tool Execution 会额外带上 MCP transport / server metadata，用于 telemetry、错误处理和 auth 状态维护。

D. runToolUse()：单调用公共入口

这是整个目录中最重要的函数之一。上层的两个 scheduler 最终都调用它。

  1. 通过 findToolByName() 在当前可用 Tool Pool 中查找 Tool。
  2. 若没找到，会检查 base tools 中的 deprecated alias，用于兼容旧 transcript 中的旧工具名。
  3. 提取 message/request/MCP metadata。
  4. 未知 Tool：直接生成带 tool_use_id 的 error tool_result，而不是让整个 Agent Runtime crash。
  5. 检查当前 query abort signal；若已取消，生成取消结果。
  6. 正常情况下进入 streamedCheckPermissionsAndCallTool()。
  7. 最外围 catch 把意外 runtime exception 再封装成 Tool Error Message。
关键架构点：runToolUse() 是所有 Tool 类型的统一入口。 Read、Edit、Bash、Skill、MCP Tool 等虽然内部 call() 不同，但都共享同一套前后处理协议。

E. streamedCheckPermissionsAndCallTool()

这个函数本身不负责核心权限逻辑，而是一个Async Streaming Adapter。 源码注释也明确承认这是一种桥接做法：底层执行函数通过 callback 发 progress， 最终又返回结果数组；这里用一个 Stream 把两者统一成一个 AsyncIterable。 

checkPermissionsAndCallTool()
    │
    ├── onToolProgress(progress)
    │        ↓
    │    stream.enqueue(progress message)
    │
    └── Promise<final messages>
             ↓
        stream.enqueue(final messages)
             ↓
          stream.done()

系统意义：上层 scheduler 不需要知道某个 Tool 的 progress callback 细节， 只要统一 for await 消费更新即可。

F. buildSchemaNotSentHint()

这个函数处理一个非常 Claude Code 特有的场景：ToolSearch / deferred tools。 如果某个 Tool 虽然本地存在，但它的 schema 并没有真正出现在送给模型的工具集合中， 模型可能把 array、number、boolean 等参数错误地产生为 string。 当 Zod validation 失败时，该函数会根据历史 discovered-tool set 判断是否属于这种情况， 并在错误结果中提示模型先加载 Tool schema 再重试。

系统意义：这不是单纯“参数校验失败”，而是把失败原因重新反馈给模型，帮助 Agent 自修复。

G. checkPermissionsAndCallTool()：执行主体

这是整个单 Tool 生命周期最复杂的函数。可以按以下阶段理解：

阶段执行内容为什么需要
1. Schema Validationtool.inputSchema.safeParse(input)阻止 LLM 生成的错误参数直接进入业务函数。
2. Tool Validationtool.validateInput?.()Schema 只能校验结构；Tool 自己可以校验路径、范围、业务约束等语义。
3. Speculative CheckBash permission classifier 可提前启动让 classifier 与 Hooks / permission UI 准备并行，降低延迟。
4. Input Preparation处理内部字段、backfill observable input让 Hook/Permission 看见必要派生字段，同时避免无意改变最终 transcript。
5. Pre HooksrunPreToolUseHooks()允许外部策略修改输入、允许/拒绝/ask、补充上下文或停止 continuation。
6. PermissionresolveHookPermissionDecision()把 Hook 决策、settings rules、需要交互的 Tool、用户确认统一起来。
7. Denial path生成 error result；特定 classifier denial 还可执行 PermissionDenied hooks拒绝也是一个可反馈给模型的观察结果，而不是程序异常。
8. Executetool.call()真正执行 Tool 实现，并转发 progress。
9. Result Mapping结构化结果、API ToolResult block、结果大小、文件扩展名等把异构 Tool 输出统一成模型下一轮能消费的消息格式。
10. Post HooksrunPostToolUseHooks()成功后允许追加上下文、停止后续、修改 MCP output 等。
11. Error path错误分类、MCP auth 更新、failure hooks使错误可恢复、可观测，并允许外部 Hook 在失败后介入。

runToolUse()
  ↓
streamedCheckPermissionsAndCallTool()
  ↓
checkPermissionsAndCallTool()
  ↓

1.5 Context Modifier 的产生

Tool 的调用结果可能带有 contextModifier。 toolExecution.ts 不负责最终决定多个 modifier 的应用顺序， 而是把 modifier 放进 MessageUpdateLazy 返回给 scheduler。 因此上下文更新的“生成”和“调度应用”被拆成两层： 

Tool.call()
   ↓
result.contextModifier
   ↓
toolExecution.ts 封装
   ↓
toolOrchestration / StreamingToolExecutor
   ↓
按调度语义修改 ToolUseContext

1.7 该脚本在整个系统中的作用

系统定位：toolExecution.ts 是 Tool Runtime 的“事务执行内核”。 它保证不管上层使用 batch scheduler 还是 streaming scheduler， 每一个 Tool Call 都执行同一套 Schema、Hook、Permission、Telemetry、Result 与 Error 协议。

如果没有这一层，上层 Agent Loop 就必须分别为 Bash、Read、Edit、MCP 重复实现权限、错误、Hook 和消息封装， 系统会迅速失去一致性。

源码入口： toolExecution.ts

2. toolHooks.ts

Hook / Permission 适配层

2.1 脚本的核心作用

toolHooks.ts 位于“底层 Hook engine”和“Tool Execution pipeline”之间。 它不是 Tool Scheduler，也不是直接执行 shell hook command 的底层实现； 它更像一个Hook 语义适配器： 把 executePreToolHooks()、executePostToolHooks() 等底层输出， 转换成 Tool Runtime 可以消费的强类型事件。 

底层 Hook Engine（utils/hooks）
        │
        ▼
   toolHooks.ts
        │
        ├── permission result
        ├── updated input
        ├── additional context
        ├── stop / prevent continuation
        ├── attachment / progress
        └── updated MCP output
        │
        ▼
 toolExecution.ts

2.2 整体结构

结构主要函数/类型作用
输出类型PostToolUseHooksResult<Output>定义 Post Hook 能产生普通消息或修改后的 MCP Tool Output。
成功后 HookrunPostToolUseHooks()Tool 成功后执行 PostToolUse Hook 并翻译结果。
失败后 HookrunPostToolUseFailureHooks()Tool exception / abort 后执行 Failure Hook。
权限合并resolveHookPermissionDecision()把 Hook allow/ask/deny 与 rule-based permission、交互要求、canUseTool 合并。
执行前 HookrunPreToolUseHooks()允许 Hook 在真正 Tool Call 前修改参数、决定权限、注入 context 或阻止执行。

2.3 runPreToolUseHooks()

这是 Tool 执行之前最重要的外部扩展点。它可以产生多种事件：

事件语义
messageHook progress、attachment 等普通消息。
hookPermissionResultHook 给出 allow / ask / deny。
hookUpdatedInputHook 修改 Tool 输入，但不直接决定权限。
preventContinuation即使当前 Tool 执行完，也可以阻止 Agent 后续继续。
stopReason为停止 continuation 提供原因。
additionalContext把 Hook 产生的信息注入会话上下文。
stopHook 被中断时停止当前执行流。

调用关系：

checkPermissionsAndCallTool()
        ↓
runPreToolUseHooks()
        ↓
executePreToolHooks()   ← 更底层 Hook Engine
        ↓
把结果翻译为强类型事件
        ↓
toolExecution.ts switch(result.type)

2.4 Hook 如何修改 Tool 参数？

如果 Hook 返回 updatedInput：

  • 若同时返回 permissionBehavior，updatedInput 与该 Hook permission decision 一起进入后续 permission resolution。
  • 若没有 permissionBehavior，则产生 hookUpdatedInput，让正常权限流程继续，但后续看到的是修改后的参数。

因此 PreToolUse Hook 不只是“通知机制”，它是真正的execution interceptor。

2.5 resolveHookPermissionDecision()：最重要的安全不变量

源码明确强调：Hook 的 allow 并不意味着无条件绕过 settings.json 中的 deny/ask 规则。

它处理的主要情况：

  1. Hook = allow：先考虑 Tool 是否必须用户交互，以及当前 runtime 是否强制要求 canUseTool。
  2. 即便 Hook allow，也继续检查 rule-based permissions。
  3. 若 rule = deny，deny 覆盖 Hook allow。
  4. 若 rule = ask，仍然需要 permission dialog / canUseTool。
  5. Hook = ask：将 Hook 原因作为 forceDecision 传入正常交互流程。
  6. 没有 Hook decision：完全走普通 permission flow。
PreToolUse Hook
      │
      ├── deny ──────────────→ deny
      │
      ├── ask ───────────────→ canUseTool(...)
      │
      └── allow
            │
            ▼
    checkRuleBasedPermissions()
            │
       ┌────┼────┐
       │    │    │
      deny ask  null
       │    │    │
       ▼    ▼    ▼
      deny prompt allow

系统意义：Hook 是扩展机制，而不是一个可以意外突破核心安全策略的后门。

2.6 runPostToolUseHooks()

Tool 成功后执行。主要处理：

  • Hook 普通 message / progress。
  • blocking error attachment。
  • preventContinuation 与 stop reason。
  • additional context。
  • 对 MCP Tool 的 updatedMCPToolOutput。
  • Hook cancel / Hook execution error 的 telemetry 与 attachment。

其中 MCP output 可被 PostToolUse Hook 修改 是一个很重要的系统能力： 外部策略层可以在远程 MCP Tool 输出进入模型上下文前做转换或治理。

2.7 runPostToolUseFailureHooks()

当 Tool 执行抛出异常或被中断时，toolExecution.ts 会调用它。

它允许 Failure Hook：

  • 看到 Tool 名称、input、error 与是否 user interrupt。
  • 产生额外上下文。
  • 产生 Hook attachment / blocking information。
  • 将失败事件接入日志、自动修复、外部通知或组织策略。

2.8 为什么单独拆成 toolHooks.ts？

如果所有 Hook 语义都堆进 toolExecution.ts， 单 Tool 内核会更加庞大，而且 permission 语义容易在 REPL、主 Query Loop 等不同调用环境发生漂移。 源码注释特别指出 resolveHookPermissionDecision() 还会被其他路径复用， 目的就是让权限语义保持一致。

2.9 该脚本在整个系统中的作用

系统定位：toolHooks.ts 是 Tool Runtime 的 policy/interception layer。 它让企业策略、自定义 Hook、权限、额外上下文和执行后处理可以介入 Tool Call， 同时保持底层 Tool 实现与这些策略解耦。

源码入口： toolHooks.ts

3. toolOrchestration.ts

Batch Scheduler

3.1 脚本的核心作用

toolOrchestration.ts 是经典的模型完成一轮输出后的批量 Tool Scheduler。 它接收这一轮的全部 ToolUseBlock[]，判断每一次调用是否 concurrency-safe， 然后将连续安全调用组成 batch，并决定并发还是串行执行。 

一轮 Claude response
       ↓
ToolUseBlock[]
       ↓
partitionToolCalls()
       ↓
┌───────────────────────┐
│ safe batch            │ → concurrent
├───────────────────────┤
│ unsafe single call    │ → serial / exclusive
├───────────────────────┤
│ safe batch            │ → concurrent
└───────────────────────┘
       ↓
每个调用最终仍走 runToolUse()

3.2 整体结构

函数/类型作用
getMaxToolUseConcurrency()读取最大并发度，默认 10。
MessageUpdate调度层返回 message + 当前 newContext。
runTools()总入口：partition → concurrent/serial → context modifier merge。
Batch保存 isConcurrencySafe 与该 batch 的 Tool blocks。
partitionToolCalls()根据每次 invocation 的 isConcurrencySafe(input) 分批。
runToolsSerially()一个一个调用 runToolUse()，modifier 立即影响下一 Tool。
runToolsConcurrently()使用 async generator 并发工具 all() 驱动多个 runToolUse()。
markToolUseAsComplete()维护 in-progress Tool ID 集合。

3.3 getMaxToolUseConcurrency()

最大并发来自：

CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY

未配置时默认值为 10。

系统作用：即使模型一次生成大量并发安全调用，也避免无限创建进程、文件 I/O 或网络/MCP 请求。

3.4 partitionToolCalls()

这是这个脚本最关键的算法。

对每个 Tool Call：

  1. 从当前 Tool Pool 找到 Tool。
  2. 先用 inputSchema.safeParse() 解析参数。
  3. 只有 Schema 成功时才调用 tool.isConcurrencySafe(parsedInput.data)。
  4. 若判断函数异常，则保守返回 false。
  5. 当前调用 safe 且上一个 batch 也 safe：加入上一 batch。
  6. 否则新建 batch。
Read A  safe ─┐
Read B  safe ─┼── Batch 1 concurrent
Grep C  safe ─┘

Edit D unsafe ─── Batch 2 serial/exclusive

Read E  safe ─┐
Read F  safe ─┘── Batch 3 concurrent
注释与实际实现的差异： 源码注释仍写“read-only tools / non-read-only tool”， 但真实判断条件已经是 isConcurrencySafe(input)。 阅读时应以实际代码为准：并不是所有 read-only 一定 safe，也不是只能靠静态 Tool 类型判断。

3.5 为什么是连续 batch，而不是把所有 safe Tool 抽出来？

例如模型输出：

Read A
Edit B
Read C

不能重排为：

Read A + Read C
Edit B

因为 Read C 可能就是为了读取 Edit B 修改后的结果。

因此 scheduler 保留模型 Tool Call 的原始顺序语义，unsafe Tool 自然形成一个 barrier。

3.6 runToolsSerially()

串行路径对每一个 Tool 依次执行 runToolUse()。 如果一个 Tool 返回 contextModifier，它会立刻修改 currentContext， 因此下一个 Tool 使用的是新 Context。 

Tool A
  ↓
runToolUse(A)
  ↓
contextModifier A
  ↓
currentContext = A(currentContext)
  ↓
Tool B 使用新 Context

系统意义：保证依赖前序状态的 mutation Tool / context-changing Tool 有明确 happens-before 关系。

3.7 runToolsConcurrently()

并发路径使用项目里的 async generator all()，而不是简单 Promise.all()。 每个并发分支内部仍执行同一个 runToolUse()， 从而可以继续向上游 yield progress 和结果。

最大并发度由前述配置控制。

3.8 并发 batch 的 Context Modifier 如何处理？

这是该脚本一个非常关键但容易忽略的细节。 并发 Tool 执行过程中，不能让先返回的 Tool 立即修改其他仍在运行 Tool 的 Context， 否则结果会取决于“哪个网络请求先完成”，产生非确定性。

所以 runTools() 会：

  1. 先按 toolUseID 暂存 concurrent batch 中产生的 modifiers。
  2. 并发 batch 全部结束后，再按原始 blocks 顺序应用 modifiers。
Concurrent:
A ───── finish second → modifier A
B ─ finish first      → modifier B

不是按完成时间：
B modifier → A modifier

而是按原始模型顺序：
A modifier → B modifier

系统意义：并发执行获得性能，但 Context 合并保持 deterministic semantics。

3.9 该脚本在整个系统中的作用

系统定位：toolOrchestration.ts 是传统 batch Tool Scheduler。 它解决的是“模型一次产生多个 Tool Call 后如何安全地利用并发”， 而不是重复实现 Tool 的 Schema、Permission 或 Hook。 这些全部委托给 runToolUse()。

源码入口： toolOrchestration.ts

4. StreamingToolExecutor.ts

Streaming Stateful Scheduler

4.1 为什么还需要另一个 Scheduler？

传统 runTools() 要等模型一整轮 streaming response 完成，收集到所有 ToolUseBlock 后再执行。 但模型可能已经早早生成了一个完整的 Read/Bash Tool Call， 此时继续等待后续 token 会浪费 latency。

StreamingToolExecutor 的目标是：

某个 Tool Call 一旦在模型流中完整出现，就尽可能立刻启动，而不是等待整轮模型输出结束。 
传统：
Claude streaming ████████████████████
                                Tool A █████
                                       Tool B █████

Streaming executor：
Claude streaming ████████████████████
         Tool A █████
               Tool B █████

4.2 整体结构

文件主要由一个状态化类和几个内部类型构成：

结构作用
MessageUpdatestreaming scheduler 对外产生 message / newContext。
ToolStatusqueued → executing → completed → yielded 状态机。
TrackedTool保存 ToolUseBlock、assistant message、并发安全性、promise、results、progress、modifiers。
StreamingToolExecutor队列调度、执行、abort、progress、结果排序的主体。
markToolUseAsComplete()维护 in-progress ID 集合。

4.3 类的主要状态字段

字段作用
tools按模型接收顺序保存所有 TrackedTool，是顺序语义的基础。
toolUseContext当前 Tool Runtime Context，非并发 Tool 的 modifier 可以更新它。

4.4 addTool()

当 query.ts 在模型流中拿到完整 tool_use block，就调用该方法。

它执行：

  1. 查找 Tool definition。
  2. 未知 Tool：直接构造 completed error result。
  3. Schema parse。
  4. 调用 isConcurrencySafe(parsedInput)；异常时按 false。
  5. 创建状态为 queued 的 TrackedTool。
  6. 调用 processQueue() 尝试立即启动。

4.5 canExecuteTool()：核心并发规则

逻辑可以抽象为：

如果当前没有 Tool executing：
    新 Tool 可以执行

否则：
    只有“新 Tool 是 safe”
    且“所有正在 executing 的 Tool 都 safe”
    才能执行

因此：

当前执行新 Tool结果
无safe / unsafe可以启动
全部 safesafe可并发启动
全部 safeunsafe等待
存在 unsafesafe等待
存在 unsafeunsafe等待

这意味着 unsafe Tool 获得了exclusive access。 它既不会和前面的 Tool 并发，也阻止后面的 Tool 越过自己。

4.6 processQueue()

遍历 tools 队列，对 queued Tool 调用 canExecuteTool()。 如果可以则 executeTool()。 如果当前遇到一个不能执行的 unsafe Tool，则停止继续向后调度。

这使 unsafe Tool 成为一个 Concurrency Barrier： 后面的 safe Read 也不能跨过一个正在等待的 Edit/Bash mutation。

4.7 discard()

当模型 streaming 请求发生 fallback/retry 时，之前已经开始执行的 Tool Call 与旧 tool_use_id 属于失败的 assistant response。 如果这些结果继续流出，就会形成 orphan tool_result。

所以 query.ts 会调用 discard()， queued Tool 不再启动；in-progress Tool 最终收到 synthetic streaming-fallback error。 然后 query 创建一个全新的 executor。

4.8 Abort / Synthetic Error 体系

该类区分几类取消原因：

  • sibling_error：并行 sibling（特别是 Bash）失败。
  • user_interrupted：用户中断/拒绝。
  • streaming_fallback：当前模型流被废弃并重试。

createSyntheticErrorMessage() 会为未真正完成的 Tool 补一个合法 tool_result。

为什么重要：Anthropic Tool Use 对话协议要求 tool_use 与 tool_result 成对。 即使任务被中断，Runtime 也不能留下只有 tool_use 没有对应 result 的不完整 transcript。

4.9 getToolInterruptBehavior() 与 interruptible state

Tool 可以定义中断行为 cancel 或 block。 如果没有定义或判断异常，源码保守地按 block。 updateInterruptibleState() 会根据当前 executing tools 更新 UI/runtime 是否存在“可中断 Tool”。

4.10 executeTool()：Streaming Scheduler 的实际执行器

主要流程：

status = executing
  ↓
登记 in-progress ID
  ↓
检查是否已经 abort/discard
  ↓
创建 per-tool child AbortController
  ↓
runToolUse(...)
  ↓
for await updates
  ├── progress → pendingProgress
  ├── normal result → messages
  ├── contextModifier → 暂存
  └── error result → 判断是否触发 sibling cancellation
  ↓
status = completed
  ↓
Promise finally → processQueue() 启动后续 Tool

4.11 为什么 Bash error 会取消 sibling，而 Read error 不会？

源码明确把 Bash 作为特殊情况。 原因是多条 shell command 往往存在隐式依赖链： 前一步创建目录/编译失败后，后续命令继续运行可能无意义甚至产生误导结果。

而 Read/WebFetch 等调用通常彼此独立，一个失败不应该自动杀掉全部 sibling。

Bash A error
   ↓
hasErrored = true
   ↓
siblingAbortController.abort("sibling_error")
   ↓
其他相关 subprocess 快速取消

4.12 Context Modifier 在 Streaming 路径中的处理

这里与 toolOrchestration.ts 有一个值得注意的差异。 源码注释明确说当前 streaming executor 暂不支持 concurrent tools 的 context modifiers。 只有非 concurrency-safe Tool 返回 modifier 时，才直接更新 executor 内的 toolUseContext。

对比： 传统 batch scheduler 会缓存 concurrent batch 的 modifiers，batch 完成后按原始 Tool 顺序应用； Streaming executor 当前则不应用 concurrent Tool 的 modifiers。 这是两个 scheduler 在 Context merge 能力上的一个实际差异。

4.13 getCompletedResults()

非阻塞地取出已经完成但尚未 yield 的结果。

两个关键规则：

  • Progress message 不需要等最终结果，尽快向上游 yield。
  • 普通结果要维护必要的接收顺序；如果遇到正在执行的 unsafe Tool，会停止向后 yield。

这体现了一个重要区分：执行可以并发，结果暴露给 Agent Runtime 时仍需要保持语义顺序。

4.14 getRemainingResults()

模型响应结束后，query.ts 会调用它等待剩余 Tool。 它反复：

  1. processQueue() 尝试启动能运行的 queued Tool。
  2. yield 已完成结果。
  3. 如果还有 executing Tool 但暂无完成结果/进度，则 Promise.race() 等待任意 Tool 完成或 progress 到达。
  4. 直到所有 Tool 进入 yielded。

4.15 与 query.ts 的关系

query.ts 根据 feature gate 创建 StreamingToolExecutor。 模型流中每出现一批完整的 tool_use blocks，就调用 addTool()； Streaming 期间还不断调用 getCompletedResults() 提前向 UI / transcript 输出结果。 模型流结束后再调用 getRemainingResults() 收尾。 

query.ts
  │
  ├── model streaming message
  │       ↓
  │   tool_use block
  │       ↓
  │   addTool()
  │       ↓
  │   Tool 可能已开始执行
  │
  ├── getCompletedResults()  ← streaming 中不断拿完成结果
  │
  └── response 完成
          ↓
      getRemainingResults()
          ↓
      等全部 Tool 收尾

4.16 该脚本在整个系统中的作用

系统定位：StreamingToolExecutor.ts 是低延迟 Tool Scheduler。 它把 Tool Execution 从“模型整轮响应之后的阶段”前移到“模型生成过程中的事件”， 从而形成 model generation 与 tool execution 的 pipeline overlap。

源码入口： StreamingToolExecutor.ts

7.2 它们共同解决的不是“Tool 能做什么”，而是“Tool 如何成为可靠 Runtime 能力”

一个具体 BashTool 只需要知道如何执行 command； 但是生产级 Agent Harness 还必须处理：

  • LLM 参数是否合法。
  • Tool 调用是否符合语义约束。
  • 是否允许用户/策略执行。
  • 是否能与其他 Tool 并发。
  • 中断时如何补齐 tool_result。
  • 进度如何实时显示。
  • 错误是否应触发 sibling cancellation。
  • Tool 输出如何进入下一轮模型上下文。
  • MCP Server auth 失败后状态如何更新。
  • 企业 Hook 如何在执行前后介入。
  • 如何保证 telemetry 有价值又不过度泄露敏感数据。

这四个脚本正是把这些“Tool 能力外围的工程治理”集中到 Runtime 层。

  • StreamingToolExecutor.ts：模型还没说完时，怎么提前执行 Tool 并维持并发、取消和结果顺序。
