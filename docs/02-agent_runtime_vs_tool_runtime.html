Claude Code 中 Agent Runtime 与 Tool Runtime 的作用和区别

本文基于 BennettBin/Claude-code 恢复源码，对 Claude Code 中 Agent Runtime 与 Tool Runtime 的职责边界、调用链、工程意义和自研 Agent Harness 的架构启示进行系统梳理。

核心结论：Agent Runtime 负责“整个智能体如何持续运行”；Tool Runtime 负责“某一次工具调用如何被安全、正确地执行”。

注意：BennettBin/Claude-code 并非 Anthropic 官方开源仓库，而是依据公开发布物与 source map 恢复出的 TypeScript 源码树，因此本文把其中实现视为“恢复源码中可观察到的工程结构”。

1. 两者不是平行关系，而是上下层关系

从架构上看，Agent Runtime 与 Tool Runtime 不是两个彼此独立的执行系统，而是明显的控制层—执行层关系。

Agent Runtime 决定“接下来做什么、是否继续循环”；Tool Runtime 决定“这个 Tool Call 到底怎么执行”。

当模型产生一个 tool_use 时，Agent Runtime 并不直接执行 Bash、Read、Edit 或 MCP Tool，而是把这个动作交给 Tool Runtime。Tool Runtime 完成校验、权限、并发调度、真正执行、错误处理和 tool_result 标准化之后，再把结果交还给 Agent Runtime。

2. Agent Runtime：负责整个 Agent 的运行生命周期

在这份源码中，Agent Runtime 的核心主要可以从以下文件观察：

src/QueryEngine.ts
src/query.ts

可以把 QueryEngine 理解为 conversation / session 级别的运行门面，而真正的 ReAct 风格 Agent Loop 主要由 query() 和 queryLoop() 驱动。

2.1 Agent Runtime 管理什么？

  • Conversation / Messages
  • System Prompt 与动态上下文
  • 模型调用与 Streaming
  • 模型输出中的 text / thinking / tool_use
  • Tool 调用之后的 tool_result 回填
  • Agent Loop 是否继续
  • Token / Cost / Budget
  • Context Compression / Compact
  • Retry / Recovery
  • Skill / Subagent / Multi-Agent 协调
  • 最终任务终止条件

2.2 它本质上管理的是 Control Flow

准备 Context
    ↓
调用 Claude
    ↓
Claude 返回 text / thinking / tool_use
    ↓
如果存在 tool_use
    ↓
调用 Tool Runtime
    ↓
获得 tool_result
    ↓
写回 messages
    ↓
再次调用 Claude
    ↓
直到模型完成任务或触发终止条件

因此，Agent Runtime 最核心的职责不是“执行某个工具”，而是维护 Reasoning → Action → Observation → Reasoning 的全局状态机。

3. Tool Runtime：负责一次 Tool Call 的完整执行生命周期

Tool Runtime 主要集中在：

src/Tool.ts
src/services/tools/toolExecution.ts
src/services/tools/toolOrchestration.ts

假设模型返回：

{
  "type": "tool_use",
  "name": "Bash",
  "input": {
    "command": "git status"
  }
}

Claude Code 不会让 Agent Loop 直接调用系统命令，而是把该 tool_use 送入 Tool Runtime。

3.1 Tool Runtime 的典型执行链

tool_use
   ↓
查找对应 Tool
   ↓
Schema Validation
   ↓
Tool-specific validateInput()
   ↓
Permission Check
   ↓
Hooks / Safety
   ↓
Concurrency Scheduling
   ↓
execute()
   ↓
捕获异常
   ↓
格式化 tool_result
   ↓
返回 Agent Runtime

所以 Tool Runtime 解决的不是“下一步应该使用什么能力”，而是：既然已经决定调用这个 Tool，这个 Tool 如何可靠地运行。

4. Agent Runtime 与 Tool Runtime 的核心区别

维度Agent RuntimeTool Runtime
核心职责Agent 编排与生命周期管理Tool 执行与执行治理
解决的问题下一步做什么、是否继续这个 Tool Call 怎么正确运行
核心文件query.ts, QueryEngine.tsTool.ts, toolExecution.ts, toolOrchestration.ts
生命周期整个任务 / 会话一次或一批 Tool Call
是否调用 LLM是通常否
是否维护 Messages是主要负责返回 tool_result

Context Compression负责不负责

Permission携带上下文 / 发起调用执行实际权限检查

错误处理根据结果决定继续、重试或重新规划捕获、归一化并返回 Tool 执行错误
简化理解：Agent Runtime 是“总调度器”；Tool Runtime 是“动作执行基础设施”。

5. 为什么 Claude Code 要把 Tool Runtime 单独拆出来？

如果 Agent Runtime 直接执行各类工具，很容易变成大量硬编码：

if (tool.name === "Bash") {
    runBash(...)
}

if (tool.name === "Read") {
    readFile(...)
}

if (tool.name === "Edit") {
    editFile(...)
}

这种设计的问题是 Agent Loop 会同时承担模型编排、权限、安全、工具执行、重试、并发、Schema 校验等职责，很快演变成一个难以维护的“巨型控制器”。

Claude Code 更接近的方式是：定义统一的 Tool abstraction，再由 Tool Runtime 统一执行。恢复源码中可以看到 Tool 具备类似以下能力：

inputSchema
validateInput(...)
checkPermissions(...)
isConcurrencySafe(...)
isReadOnly(...)
isDestructive(...)
...

这意味着 Agent Runtime 不需要了解每一个工具的底层执行细节，只需要处理一个抽象动作：

模型决定调用 Tool
        ↓
Agent Runtime 把 Tool Call 交给 Tool Runtime
        ↓
Tool Runtime 按统一协议执行

这本质上是软件工程中的 Separation of Concerns。

6. Tool Runtime 还承担并发调度

Claude 一次响应可以产生多个 Tool Call，例如：

Read A
Read B
Grep C
Edit D
Read E

Tool Runtime 不应该简单地把所有调用都 Promise.all()，因为有些操作只读、可并发，有些操作会修改文件或外部状态，不适合并发。

Claude Code 的 Tool orchestration 会调用类似 tool.isConcurrencySafe(input) 的能力判断 Tool 是否可以并发。

Read A ─┐
Read B ─┼── parallel batch
Grep C ─┘

Edit D ───── serial

Read E ───── next batch

因此 Tool Runtime 不只是“执行器”，还是一个局部的 Tool Scheduler / Execution Orchestrator。

8. 用一个实际任务理解

例如用户输入：

帮我找到这个项目中的 bug 并修复。

第一轮

Claude:
我需要先查看项目结构。

tool_use:
Glob(**/*.ts)

Agent Runtime 发现 tool_use，将调用交给 Tool Runtime。

Tool Runtime：

找到 Glob Tool
→ Schema 校验
→ Permission
→ Execute
→ 返回文件列表

然后 Agent Runtime 把结果放回 messages，再次调用 Claude。

第二轮

tool_use:
Read(src/query.ts)
Read(src/utils.ts)
Read(src/config.ts)

Tool Runtime 判断这些 Read 调用可以并发，于是并行执行。

第三轮

Claude:
发现 src/utils.ts 中存在问题。

tool_use:
Edit(...)

Edit 属于 mutation 类动作，Tool Runtime 会执行更严格的权限和串行控制。

最终

Tool Runtime 返回修改结果，Agent Runtime 再次调用模型。模型判断任务已完成，没有继续产生 Tool Call，于是 Agent Loop 结束。

9. Tool 与 Tool Runtime 不是同一个概念

Tool
=
一个能力定义
例如 BashTool / ReadTool / EditTool / MCPTool

Tool Runtime
=
管理这些 Tool 如何被发现、校验、授权、调度、执行和返回结果的基础设施

同理：

Agent
=
Model + Prompt + Context + Tools + Policy

Agent Runtime
=
让这个 Agent 持续运行起来的控制基础设施

10. 自研 Agent Harness 时可以怎样分层？

AgentRuntime
├── AgentLoop
├── ContextManager
├── ModelRuntime
├── MemoryManager
├── SkillManager
├── SubagentManager
└── ToolRuntime
      ├── ToolRegistry
      ├── SchemaValidator
      ├── PermissionManager
      ├── ToolScheduler
      ├── ToolExecutor
      ├── RetryManager
      └── ResultNormalizer

这种拆分的优点是：模型推理、上下文管理和 Tool 执行之间形成清晰边界。后续无论新增 MCP、Browser、Database、Shell、Code Execution 或企业内部 Tool，都不需要修改核心 Agent Loop。

11. 面试时可以如何概括？

Agent Runtime 负责 Agent 的全局运行生命周期，包括模型调用、上下文管理、Agent Loop、Tool Call 编排、状态维护、上下文压缩、Subagent 与终止控制；Tool Runtime 则负责 Action 的局部执行生命周期，包括 Tool 查找、参数 Schema 校验、权限、安全检查、并发调度、实际执行、错误处理以及 tool_result 标准化。前者解决“下一步做什么”，后者解决“这个动作怎么正确执行”。

在 Claude Code 中，可以把 queryLoop() 看作 Agent Runtime 的核心控制循环，而把 runTools() / runToolUse() 一类逻辑看作 Tool Runtime 的核心执行入口。
