Claude Code Tool Runtime

Concurrency Orchestration：源码在哪里，它是怎么工作的？

本文基于 BennettBin/Claude-code 恢复源码，系统梳理 Claude Code Tool Runtime 中的并发编排机制， 包括传统 Batch Tool Orchestration 与 Streaming Tool Execution 两套路径，以及 isConcurrencySafe()、partitionToolCalls()、 runToolsConcurrently()、StreamingToolExecutor 等核心实现。

核心结论：Claude Code 不是简单把所有 Tool Call 用 Promise.all() 并行执行，而是先对每次调用做运行时并发安全判断，再通过 batch、barrier、队列和独占执行机制维持语义正确性。

注意：BennettBin/Claude-code 并非 Anthropic 官方开源仓库，而是根据公开发布物与 source map 恢复出的 TypeScript 源码树。

1. Concurrency Orchestration 的核心源码位置

传统 Tool 并发编排主要集中在：

src/services/tools/toolOrchestration.ts

最值得看的函数包括：

runTools()
partitionToolCalls()
runToolsConcurrently()
runToolsSerially()
getMaxToolUseConcurrency()

另外，每个 Tool 是否允许并发的基础接口位于：

src/Tool.ts

而 Streaming Tool Execution 主要位于：

src/services/tools/StreamingToolExecutor.ts
src/query.ts
可以把整个机制分成两层：Tool 自己声明并发安全性，Tool Runtime 根据这个声明完成调度与执行。

2. 第一步：每个 Tool 自己声明是否可以并发

Claude Code 并不是根据 Tool 名字硬编码判断是否并发，而是调用：

tool.isConcurrencySafe(input)

这意味着并发安全是 Tool abstraction 的一部分。更重要的是，它是一个按调用参数动态判断的接口。

Tool 层还采用了 fail-closed 默认值：

isConcurrencySafe: (_input?: unknown) => false
isReadOnly:        (_input?: unknown) => false

含义是：

如果一个新 Tool 没有明确声明自己可以并发，那么默认按“不安全、不可并发”处理。

这是一种典型的安全系统设计：无法证明安全时，不默认放行。

3. 为什么不是简单地用 isReadOnly 判断？

很多人会把并发调度简单理解成：

Read  → 并发
Write → 串行

但源码真正使用的是：

isConcurrencySafe(input)

而不是：

isReadOnly(input)

两者概念相关，但不是同一个东西。因为同一个 Tool 在不同参数下，副作用可能不同。

例如 Bash：

Bash("ls")
Bash("rm file")

都是 BashTool，但对系统状态的影响完全不同。因此一个成熟 Agent Harness 更适合做：

ToolCall-level concurrency classification

而不只是：

Tool-level static metadata

4. partitionToolCalls()：传统批处理并发的核心算法

partitionToolCalls() 的主要职责，是按原始 Tool Call 顺序，将连续的 concurrency-safe 调用合并为并发 batch。

简化后的逻辑如下：

for each toolUse:
    找到对应 Tool

    使用 inputSchema 解析 input

    safe = tool.isConcurrencySafe(input)

    if safe
       and 上一个 batch 也是 safe:
           追加到上一个 batch
    else:
           新建 batch

更接近源码意图的关键逻辑：

const tool =
    findToolByName(toolUseContext.options.tools, toolUse.name)

const parsedInput =
    tool?.inputSchema.safeParse(toolUse.input)

const isConcurrencySafe =
    parsedInput?.success
        ? tool.isConcurrencySafe(parsedInput.data)
        : false

这里有两个重要防御策略：

  • 如果 inputSchema.safeParse() 失败，默认认为不可并发。
  • 如果 isConcurrencySafe() 内部发生异常，也按不可并发处理。
核心原则：无法证明 safe，就按 unsafe 处理。

5. 为什么只合并“连续的”并发安全 Tool？

假设模型一次返回：

1. Read A
2. Read B
3. Grep C
4. Edit D
5. Read E

若：

Read  → safe
Grep  → safe
Edit  → unsafe

那么会被分组为：

Batch 1
┌───────────┐
│ Read A    │
│ Read B    │
│ Grep C    │
└───────────┘
concurrent

Batch 2
┌───────────┐
│ Edit D    │
└───────────┘
serial

Batch 3
┌───────────┐
│ Read E    │
└───────────┘
concurrent

非常重要的一点是，Claude Code 不会把所有 Read 全部“抽出来”放到一起执行。

比如：

Read A
Edit B
Read C

不会被重排为：

Read A + Read C
Edit B

而是保持：

Read A
   ↓
Edit B
   ↓
Read C

这是为了保持模型生成 Tool Call 时的原始执行语义，避免跨越 mutation 操作导致读取错误状态。

6. runTools()：决定并发还是串行执行

在 batch 分组之后，runTools() 会根据每个 batch 的并发安全标记选择执行方式：

for (batch of partitionToolCalls(...)) {

    if (batch.isConcurrencySafe) {
        runToolsConcurrently(...)
    } else {
        runToolsSerially(...)
    }
}

可以抽象成：

                    partitionToolCalls()
                           │
                ┌──────────┴──────────┐
                │                     │
            safe=true             safe=false
                │                     │
                ▼                     ▼
   runToolsConcurrently()     runToolsSerially()

也就是说，partitionToolCalls() 负责分类，runTools() 负责调度。

7. runToolsConcurrently()：不是简单 Promise.all()

并发执行时，源码不是简单：

Promise.all(...)

而是使用支持 AsyncGenerator 的并发执行器，大致行为可以理解为：

yield* all(
    toolUseMessages.map(async function* (toolUse) {

        setInProgress(toolUse.id)

        yield* runToolUse(...)

        markToolUseAsComplete(...)

    }),

    getMaxToolUseConcurrency()
)

这里每个 Tool 最终仍然走统一执行入口：

runToolUse()

区别只是多个 runToolUse() 会由并发调度器同时驱动。

runTools()
   │
   ▼
partitionToolCalls()
   │
   ├── concurrent batch
   │       │
   │       ▼
   │ runToolsConcurrently()
   │       ├── runToolUse(A)
   │       ├── runToolUse(B)
   │       └── runToolUse(C)
   │
   └── serial batch
           │
           ▼
     runToolsSerially()
           │
           ▼
       runToolUse(D)

8. 最大并发数为什么默认是 10？

源码中存在：

function getMaxToolUseConcurrency(): number {
    return (
        parseInt(
            process.env.CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY || '',
            10,
        ) || 10
    )
}

默认最大并发数：

10

并且可以通过环境变量调整：

CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY

这样做是为了避免一次产生大量 Tool Call 时占满：

  • 文件句柄
  • 本地进程
  • CPU / I/O
  • 网络连接
  • MCP Server 请求能力

所以即使模型一次生成 50 个安全的读取调用，也不会无上限地全部同时启动。

9. runToolsSerially() 为什么要真正串行？

串行路径本质上是：

for (const toolUse of toolUseMessages) {

    for await (const update of runToolUse(...)) {
        ...
    }

}

也就是说：

Tool A 完全完成
        ↓
Tool B 才开始
        ↓
Tool B 完全完成
        ↓
Tool C 才开始

这对 mutation Tool 尤其重要。例如：

Edit file A
↓
Bash npm test

如果同时执行，测试可能读到尚未完成修改的文件。串行执行确保：

Edit
████████████

            npm test
            ███████████

即形成明确的 happens-before 关系。

10. contextModifier：为什么有些 Tool 必须形成 barrier

某些 Tool 执行后还可以返回：

contextModifier

用于改变后续 Tool 的执行上下文，例如：

  • cwd
  • 环境变量
  • Permission state
  • Session state
  • Runtime context

串行执行时，可以形成：

Tool A
   │
   ▼
contextModifier
   │
   ▼
newContext
   │
   ▼
Tool B

如果 A、B 并发，B 可能已经在旧 context 下启动。因此这也是 Tool Runtime 必须维护顺序和 barrier 的原因之一。

11. StreamingToolExecutor：更进一步的并发执行路径

除了传统 batch 模式，源码中还有更高级的 Streaming Tool Execution：

src/services/tools/StreamingToolExecutor.ts

它解决的问题是：

为什么一定要等 Claude 整个 response 流式输出完成，才开始执行已经完整生成的 Tool Call？

传统模式：

Claude streaming
████████████████████████

                        Read A
                        █████

                             Read B
                             █████

Streaming Tool Execution：

Claude streaming
████████████████████████

       Read A
       █████

           Read B
           █████

也就是说，模型还在继续生成后面的内容时，前面已经完整生成的 Tool Call 可以提前启动。

12. query.ts 如何接入 Streaming Tool Execution

query.ts 中通过 feature gate 控制这一能力：

const useStreamingToolExecution =
    config.gates.streamingToolExecution

开启后会创建：

new StreamingToolExecutor(...)

当模型流式输出过程中出现一个完整 tool_use block 时，会调用：

streamingToolExecutor.addTool(toolBlock, message)

所以在 Streaming 路径中，Agent Runtime 与 Tool Runtime 的连接点不是“整轮模型输出结束”，而是：

一个完整 tool_use block 出现
        ↓
立即进入 Tool Runtime

13. StreamingToolExecutor 内部的状态机

每个 Tool Call 会维护类似以下状态：

type ToolStatus =
    | 'queued'
    | 'executing'
    | 'completed'
    | 'yielded'

生命周期：

addTool()
   │
   ▼
 queued
   │
   ▼
executing
   │
   ▼
completed
   │
   ▼
 yielded

每个调用还会记录：

isConcurrencySafe
promise
results
pendingProgress
contextModifiers

因此这已经不是一个简单的批量执行函数，而是一个有状态 Tool Scheduler。

14. canExecuteTool()：Streaming Scheduler 的核心判定

逻辑可以简化为：

private canExecuteTool(
    isConcurrencySafe: boolean
): boolean {

    const executingTools =
        当前正在运行的工具

    return (
        executingTools.length === 0
        ||
        (
            isConcurrencySafe
            &&
            executingTools.every(
                tool => tool.isConcurrencySafe
            )
        )
    )
}

它表达了四种情况：

情况 1：没有 Tool 正在执行

executing = []

任何 Tool 都可以启动。

情况 2：当前全是 safe Tool，新 Tool 也 safe

Read A running
Read B arrives

允许并发：

Read A ███████████
Read B    ███████████

情况 3：safe Tool 正在跑，新 Tool unsafe

Read A running
Edit B arrives

Edit 必须等待：

Read A ███████████
                   Edit B ███████

情况 4：unsafe Tool 正在跑，新 Tool 即使 safe 也不能启动

Edit A running
Read B arrives

Read B 也必须等待。换句话说：

Unsafe Tool 获得的是一种 exclusive access（独占执行权）。

15. processQueue()：真正的 Streaming 调度器

processQueue() 会不断检查 queued Tool：

遍历 queued tools
       │
       ▼
canExecuteTool() ?
       │
   ┌───┴────┐
   │        │
 yes       no
   │        │
execute    如果前面是 unsafe Tool
           则停止继续向后调度

这一步非常关键，因为它不仅判断“某个 Tool 本身能否并发”，还要维护原始 Tool 顺序。

例如：

Read A
Edit B
Read C

即使 Read C 是 safe，也不能越过正在等待的 Edit B。否则模型原本设计的执行语义会被破坏。

16. Unsafe Tool 可以理解成 Concurrency Barrier

假设流式输出顺序是：

Read A
Read B
Edit C
Read D
Read E

那么执行波次大致是：

Read A   ██████████
Read B      ██████████

                   Edit C ███████

                          Read D ███████
                          Read E    ███████

可以抽象成：

Read wave
   ↓
Write / Unsafe barrier
   ↓
Read wave
把 unsafe Tool 理解为 Concurrency Barrier，是理解 Claude Code Tool Runtime 并发机制最直观的方法之一。

17. Streaming 模式还有 sibling cancellation

StreamingToolExecutor 中还存在：

siblingAbortController

如果某个并行执行的 Bash Tool 发生错误，调度器可以取消某些仍在运行的 sibling subprocess。

这是因为 Shell 命令往往存在隐式依赖。例如：

mkdir build
cp file build/
run build/task

如果前面的关键命令失败，后面的 sibling command 继续执行可能已经没有意义。

而对 Read / WebFetch 这种通常相互独立的读取类 Tool，单个失败并不一定需要取消其他 sibling。

因此 Streaming Tool Runtime 实际上已经具有：

Concurrency-aware
+
Dependency-aware
+
Abort-aware
Tool Scheduler

19. 这套设计的工程价值

设计点解决的问题
isConcurrencySafe(input)避免简单按 Tool 名字静态判断并发安全
Fail-closed 默认值新增 Tool 未配置时不意外并发
partitionToolCalls()在保持顺序语义的前提下形成并发 batch
runToolsConcurrently()并发执行安全 Tool，同时限制最大并发度
runToolsSerially()保护有副作用和有上下文依赖的 Tool
contextModifier允许前一个 Tool 修改后续 Tool 的运行上下文
StreamingToolExecutor降低“等待整轮模型输出结束后再执行”的延迟
Unsafe barrier为 mutation Tool 提供独占执行语义
Sibling cancellation减少隐式依赖链失败后的无效执行

20. 面试时可以怎样概括

Claude Code 的 Tool Runtime 并发机制并不是简单的只读并发、写操作串行。它先通过 isConcurrencySafe(input) 对每个 Tool Call 做运行时安全分类，然后由 Tool Runtime 保持原始调用顺序进行调度。传统路径通过 partitionToolCalls() 把连续的安全调用组成 batch，再分别走并发和串行执行；Streaming 路径则通过 StreamingToolExecutor 在模型仍然输出时提前启动完整的 Tool Call，并让 unsafe Tool 形成 execution barrier，从而兼顾吞吐、延迟和执行语义正确性。
