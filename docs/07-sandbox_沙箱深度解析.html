Claude Code 的 Sandbox 是什么？如何实现？运行时起什么作用？

核心结论：Claude Code 的 Sandbox 不是独立容器，也不是简单在 Bash 前“套一层 bwrap”。它是嵌入 BashTool 执行链的 OS 级执行隔离层：上层由 Settings、Permission 和 Bash Permission 决定命令是否进入沙箱以及是否可以自动放行；sandbox-adapter.ts 把 Claude Code 的权限语义翻译成文件系统和网络策略；底层由 @anthropic-ai/sandbox-runtime 使用 macOS Seatbelt / sandbox-exec 或 Linux Bubblewrap + 网络代理约束整个进程树；执行结束后还会做 violation annotation 与安全清理。

源码边界：本文主要依据恢复源码中的 src/tools/BashTool/*、src/utils/Shell.ts、src/utils/sandbox/sandbox-adapter.ts、src/utils/permissions/pathValidation.ts 等，并用 Anthropic 官方 Sandbox Runtime 与 Claude Code Sandboxing 文档补充 OS 层实现。底层 runtime 能 sandbox 任意 process/MCP server，不代表 Claude Code 恢复源码中的产品级主接入已经覆盖所有这些场景；当前最明确的内建主链仍是 Sandboxed Bash。

一、Sandbox 的准确定位

1.1 Permission、Hook 和 Sandbox 分别控制什么？

Permission 是动作授权，Sandbox 是执行后能力约束。

1.2 为什么 Coding Agent 需要 OS 级隔离？

Bash 可以继续启动 Python、Node、Git、curl、npm script、编译器、测试框架等任意子进程。只检查最外层命令字符串无法约束后续进程树。Sandbox 把边界下沉到 OS：即使命令或子进程行为被 Prompt Injection 改变，也不能轻易越过文件和网络边界。

四、命令何时进入 Sandbox？

4.1 shouldUseSandbox()

if sandbox not enabled:
  return false

if dangerouslyDisableSandbox
   and unsandboxed commands are allowed:
  return false

if no command:
  return false

if command matches excludedCommands:
  return false

return true

所以 sandbox.enabled=true 不代表每条命令必然进入 Sandbox。单次 Tool Input 和策略会影响路由。

4.2 dangerouslyDisableSandbox

BashTool Schema 中存在该字段。只有 allowUnsandboxedCommands 允许时，它才会使本次调用不进 Sandbox；此时命令应重新依赖普通 Permission 流程，而不是自动获得无限权限。

4.3 excludedCommands 不是安全边界

源码注释明确说明它是兼容性/便利特性。某些命令可能因为运行机制与 Sandbox 不兼容而被排除，但真正安全边界仍是 Permission System + OS Sandbox Runtime。

五、Sandbox 如何和 Permission 协同？

5.1 Auto-Allow 不是无条件放行

sandbox enabled
  + autoAllowBashIfSandboxed
  + current command really sandboxed
          ↓
check sandbox auto-allow
          ├─ explicit deny → deny
          ├─ explicit ask → ask
          ├─ compound subcommand deny/ask → respect
          └─ otherwise → allow because sandboxed

设计目的：先尊重明确安全策略，再利用 OS 边界减少“每条 Bash 都点一次允许”的 approval fatigue。

5.2 Defense in Depth

Permission 管意图和产品规则，Sandbox 管真实 OS 行为。即使模型获得某条 Bash 的执行许可，进程树也只能在 Sandbox 配置允许的文件系统与网络边界内运行。

六、Settings 如何翻译成底层隔离策略？

6.1 convertToSandboxRuntimeConfig()

它会同时读取 settings.permissions、settings.sandbox、cwd、additional directories、worktree、managed policy 与内建安全规则，统一生成 SandboxRuntimeConfig。

allowWrite = ['.', ClaudeTempDir]
denyWrite = []
denyRead  = []
allowRead = []

随后再把各 settings source 中的 FileEdit/FileRead 规则与 sandbox.filesystem.* 合并进这些集合。

6.2 两套路径语义不能混淆

来源/foo 的含义
permissions.allow = ["Edit(/foo)"]Claude Code 特殊语义：相对 settings 文件目录。
sandbox.filesystem.allowWrite = ["/foo"]标准语义：绝对路径。

源码因此分别提供 resolvePathPatternForSandbox() 与 resolveSandboxFilesystemPath()。

七、保护 Claude Code 自己的控制平面

7.1 Settings 强制 denyWrite

如果 Sandbox 内脚本能修改权限或 Sandbox 配置，它就可能通过“改变策略”逃逸。因此 settings 文件和 managed settings drop-in 会被加入 denyWrite。

7.2 .claude/skills 强制 denyWrite

恢复源码明确保护 original cwd / current cwd 下的 .claude/skills。原因是 Skill 会被自动发现/加载，具有高权限执行能力；Sandbox 内不可信代码不能对它进行持久化投毒。

7.3 Git bare-repo 残留清理

源码还保护/清理 HEAD、objects、refs、hooks、config 等路径，避免 Sandbox 内构造 bare-repo 结构影响后续 unsandboxed Git。

execution restrictions
   ↓
sandboxed command
   ↓
cleanupAfterCommand()
   ↓
scrubBareGitRepoFiles()

八、网络隔离

8.1 应用层规则如何进入网络 Sandbox？

sandbox.network.allowedDomains 会直接进入 Runtime Config；同时，类似 WebFetch(domain:example.com) 的 Permission Rule 也会被转换为 Sandbox domain allowlist，使应用层 Web 权限和 Bash/curl 的底层网络限制保持一致。

8.2 底层代理模型

Sandboxed process
   ↓
HTTP proxy / SOCKS5 proxy
   ↓
allowedDomains / deniedDomains
   ├─ allowed → host network
   └─ denied/unknown → block or ask

Linux/WSL2 使用 Bubblewrap 的 network namespace，并通过 Unix Domain Socket + socat 把允许流量转给宿主代理；macOS Seatbelt 只允许访问指定 localhost proxy 端口，其他直接网络访问被系统策略阻断。底层 @anthropic-ai/sandbox-runtime 的原生 Windows alpha 则使用 Windows Filtering Platform（WFP）按 srt-sandbox SID 阻断非代理端口出站连接，再由 HTTP/SOCKS5 proxy 执行 domain allowlist。

8.3 网络越界的人机交互

SandboxPermissionRequest.tsx 专门处理 “Network request outside of sandbox”。如果企业设置 allowManagedDomainsOnly，适配层会拒绝临时放行 callback，UI 也会收缩“永久允许此域”的选项。

九、底层 OS 实现：macOS、Linux/WSL2 与 Windows

9.1 Claude Code 是适配层，不直接实现 OS Sandbox

sandbox-adapter.ts 从 @anthropic-ai/sandbox-runtime 导入 SandboxManager as BaseSandboxManager。Claude Code 负责把 Settings、Permission、cwd、Worktree、网络域名和 UI 决策转换为统一的 SandboxRuntimeConfig；底层 package 再根据操作系统选择具体的隔离后端。

Claude Code
  ↓
sandbox-adapter.ts
  ↓
SandboxRuntimeConfig
  ↓
@anthropic-ai/sandbox-runtime
  ├─ macOS backend
  ├─ Linux backend
  └─ Windows backend（底层 runtime alpha）
必须区分两个层次：
Claude Code 产品层：当前官方 Bash Sandbox 支持 macOS、Linux 和 WSL2；原生 Windows 仍不支持，Windows 用户官方路径是通过 WSL2 运行 Claude Code。
底层 @anthropic-ai/sandbox-runtime：已经提供原生 Windows alpha 后端。因此“底层 runtime 支持 Windows”不等于“Claude Code 当前已经正式支持 native Windows Sandbox”。

9.2 macOS：Seatbelt / sandbox-exec

macOS 使用 Apple Seatbelt。Sandbox Runtime 动态生成 Seatbelt Profile，再通过 sandbox-exec 启动目标进程。Profile 描述允许读取、允许写入、禁止访问以及允许连接的本地代理端口。

Claude Bash command
  ↓
generate Seatbelt profile
  ↓
sandbox-exec
  ↓
sandboxed process
  ├─ filesystem syscall → Seatbelt policy
  └─ network syscall → only allowed proxy port

Bash 后续启动的 Node、Python、Git、curl 等子进程仍继承同一 Seatbelt 边界。

9.3 Linux：Bubblewrap + Namespace + Bind Mount + Proxy

Linux 使用 Bubblewrap（bwrap）构造隔离视图，核心依赖 user namespace、mount namespace、network namespace 与 bind mount。workspace 和 session temp 等被允许的目录以 writable 方式暴露，其余区域只读或不可访问。

Host filesystem
  ↓
Bubblewrap
  ├─ user namespace
  ├─ mount namespace
  ├─ bind mounts
  └─ network namespace
  ↓
Sandbox filesystem view

网络方面，正常 network namespace 被隔离，HTTP/HTTPS/TCP 流量必须通过宿主机 HTTP/SOCKS5 proxy；Linux 中通常通过 Unix Domain Socket + socat 桥接到宿主代理。

9.4 Windows 上运行 Claude Code：官方实际路径是 WSL2

当前 Claude Code 官方文档仍明确写明 Native Windows is not supported。所以 Windows 用户启用 Claude Code Bash Sandbox 时，实际运行环境是 WSL2 中的 Linux，隔离后端仍然是 Bubblewrap：

Windows
  ↓
WSL2 Linux environment
  ↓
Claude Code
  ↓
BashTool
  ↓
Bubblewrap
  ├─ filesystem namespace
  ├─ bind mounts
  └─ network namespace
  ↓
socat / sandbox proxy

9.4.1 WSL2 的特殊问题：Windows Interop

WSL2 可以把 Windows 可执行文件的启动请求交给 Windows Host，例如 cmd.exe、powershell.exe 或 /mnt/c/Windows/System32/*。Claude Code 官方文档指出，这种 handoff 通过 Unix Socket 发生。

Sandboxed Bash in WSL2
  ↓
tries to launch powershell.exe
  ↓
WSL interop Unix socket
  ↓
seccomp / Unix-socket policy
  ├─ blocked → cannot hand off to Windows host
  └─ allowed → Windows host launches binary

因此在 WSL2 中，Bubblewrap 之外还需要治理 Unix Socket。可选 seccomp filter 能阻断相关 socket；allowAllUnixSockets 会放宽这一能力；某些与 Sandbox 不兼容的 Windows 命令也可以通过 excludedCommands 回到普通 Permission Flow。

关键理解：Windows + WSL2 场景里，Claude Code 自己并没有使用原生 Windows ACL/WFP 做产品级 Sandbox；它仍然是在 Linux Sandbox 中运行，只是必须额外防止 WSL Interop 成为跨到 Windows Host 的逃逸通道。

9.5 底层 Sandbox Runtime 的原生 Windows alpha

底层 @anthropic-ai/sandbox-runtime 已提供原生 Windows alpha。它不使用 Bubblewrap 或 Seatbelt，而是组合 Windows 自身的安全原语：

Dedicated local user
+ SID isolation
+ Restricted token
+ Job Object
+ NTFS ACL / ACE
+ Windows Filtering Platform (WFP)
+ HTTP/SOCKS5 proxy

9.5.1 专用 srt-sandbox 本地用户

一次性安装命令：

npx @anthropic-ai/sandbox-runtime windows-install

它会创建 srt-sandbox 本地账户、sandbox-runtime-users 组，并安装以该账户 SID 为匹配条件的机器级 WFP filters。密码随机生成并使用 DPAPI 加密保存。

srt-win.exe 使用两阶段启动：

Developer account
  ↓ broker
CreateProcessWithLogonW
  ↓
srt-sandbox account
  ↓
restricted token
  ↓
Job Object
  ↓
target process + child processes

目标进程不是以当前开发者身份运行，而是使用独立 SID 和独立 profile（如 %USERPROFILE%、%TEMP%、HKCU），这是 Windows 原生后端最核心的身份隔离。

9.5.2 文件系统：NTFS DACL + 显式 ACE

Windows 没有 Linux mount namespace，因此文件隔离主要依赖 NTFS discretionary ACL。srt-sandbox 默认没有开发者私人文件的权限；Runtime 只针对允许路径增加该 SID 的显式 ACE。

配置Windows 行为
filesystem.allowWrite添加继承型 MODIFY ALLOW ACE。
filesystem.allowRead添加 READ | EXECUTE ALLOW ACE。
denyRead / denyWrite添加继承型 DENY ACE，并结合父目录 FILE_DELETE_CHILD DENY 防止 rename/delete 绕过。
NTFS object
  ↓
Security Descriptor / DACL
  ↓
ACE for srt-sandbox SID
  ├─ ALLOW READ
  ├─ ALLOW MODIFY
  └─ DENY protected path

这些 ACE 是 additive 的，不覆盖原 Security Descriptor。Session 结束后 reset() 删除本次添加的 ACE；异常退出后，下次 initialize 还会做 crash-recovery cleanup。

9.5.3 网络：Windows Filtering Platform（WFP）

网络隔离由 WFP 完成。Runtime 在 FWPM_LAYER_ALE_AUTH_CONNECT_V4/V6 上安装规则：

process token contains srt-sandbox SID
  ↓
WFP ALE_AUTH_CONNECT
  ├─ loopback + proxy port range → PERMIT
  └─ all other outbound connect → BLOCK

默认只允许访问本地 proxy 端口范围（例如 60080–60089）。真正的 HTTP/SOCKS5 proxy 再做 domain allowlist：

srt-sandbox process
  ↓
127.0.0.1 proxy
  ↓
allowedDomains / deniedDomains
  ↓
Internet

因此即使程序删除 HTTP_PROXY / HTTPS_PROXY 环境变量并尝试直连，WFP 仍会在内核网络层拦截。环境变量只是“引导”，WFP 才是边界。

9.5.4 为什么独立 SID 很重要？

Windows 存在 Task Scheduler、BITS、COM 等间接进程创建路径。采用独立用户 SID 的好处是：即使子进程通过其他系统组件产生，只要仍携带 srt-sandbox SID，就继续受到 WFP 出站规则约束，并且对开发者文件没有天然访问权。

9.5.5 原生 Windows alpha 的限制

  • 这是 sandbox-runtime alpha，不是 Claude Code 产品的 native Windows Sandbox。
  • 以另一个用户运行意味着 nvm/fnm、Scoop、per-user pip、%LOCALAPPDATA% 下的工具可能无法直接读取，需要 machine-wide 安装或显式 allowRead。
  • Windows TLS/schannel 的证书吊销检查存在额外兼容性限制。
  • allowRead/allowWrite 主要以 session-level ACL grant 实现，与 Linux 每次 exec 重建 namespace 的模型不同。

十、BashTool → Shell → Sandbox Runtime

10.1 BashTool 负责决策

exec(command, abortSignal, 'bash', {
  timeout,
  preventCwdChanges,
  shouldUseSandbox: shouldUseSandbox(input),
  shouldAutoBackground
})

10.2 Shell.ts 负责真正 wrap

if (shouldUseSandbox) {
  commandString = await SandboxManager.wrapWithSandbox(
    commandString,
    sandboxBinShell,
    undefined,
    abortSignal
  )
}

因此职责非常清楚：BashTool = Tool semantics；Shell = process plumbing；SandboxManager = isolation wrapping。

10.3 执行完成后的 cleanup

if (shouldUseSandbox) {
  SandboxManager.cleanupAfterCommand()
}

Claude Code 包装的 cleanup 还会执行 bare Git repo scrub，因此 Sandbox 生命周期覆盖“执行前—执行中—执行后”。

十一、Violation 与错误反馈

BashTool 会调用 SandboxManager.annotateStderrWithSandboxFailures()，把捕获到的 Sandbox violation 与当前命令输出关联。

这样 Agent 可以区分：

程序本身报错
vs
Sandbox policy 阻止了文件/网络访问

这使 Sandbox 失败能够成为可解释的 tool_result Observation，Claude 可以请求域名权限、建议修改 allowlist、改用别的方案，或在策略允许时申请 unsandboxed fallback，而不是盲目修改业务代码。

十二、Sandbox 与其他模块的交互

12.1 Tool Runtime / Hooks

runToolUse
 → Schema
 → validateInput
 → PreToolUse Hook
 → Permission
 → BashTool.call
 → shouldUseSandbox
 → OS Sandbox

Sandbox 不是 Hook，也不绕过 Tool Runtime。它发生在真正 Bash 执行阶段。PreToolUse Hook 若改变 Bash input，后续 Permission 与 BashTool 将基于处理后的输入继续。

12.2 Permission System

  • Sandbox 可以成为 Bash Auto-Allow 的依据。
  • 显式 deny/ask 仍优先。
  • Permission 中的文件路径和 WebFetch domain 可以被下沉到底层 Sandbox policy。
  • Unsandboxed fallback 回到正常 Permission 流程。

12.3 Settings

settings change
  ↓
convertToSandboxRuntimeConfig()
  ↓
BaseSandboxManager.updateConfig()

源码订阅 settings change 并动态更新 Runtime Config；部分 refresh 路径强调同步，以减少 stale policy 的 race window。

12.4 Path Validation / File Tools

pathValidation.ts 的 isPathInSandboxWriteAllowlist() 会读取 SandboxManager.getFsWriteConfig()。如果路径已经明确在 Sandbox write allowlist 中，应用层路径 Permission 可以把它作为额外 allow 信号，同时仍尊重 denyWithinAllow。

Permission rules → Sandbox config
Sandbox config → Path permission

12.5 REPL / UI

/sandbox 是控制面：用户可以选择 Sandbox/Auto-Allow、unsandboxed fallback、查看 resolved config，并在 Linux/WSL2 检查依赖。网络越界则通过专门 Permission Dialog 回到 UI。

12.6 Git Worktree

Policy 会允许 linked worktree 对 main repo shared .git 元数据的必要写入，使 git commit 可工作；同时又针对 Git 逃逸路径增加专门清理。

12.7 MCP

底层 @anthropic-ai/sandbox-runtime 官方支持 sandbox arbitrary processes、agents 与 MCP servers；但恢复源码中 Claude Code 最明确、最成熟的内建接入是 BashTool。应区分“底层库能力”和“Claude Code 主链已集成的能力”。

十三、初始化、依赖检测与严格模式

isSandboxingEnabled() 的真实含义不是只读 sandbox.enabled，还会考虑平台、依赖和 enabled platform。

sandbox.enabled = true
   ≠
sandbox actually available

failIfUnavailable: true 可以把 Sandbox 从“增强安全”升级为“启动必须满足的安全条件”；allowUnsandboxedCommands: false 则关闭模型请求 unsandboxed 执行的 escape hatch。

Container / VM更完整环境隔离不是 Claude Code 本地 Bash Sandbox 的主要实现；本地方案强调轻量 OS primitives。

十七、对 Agent Harness 设计的启发

  1. Authorization 与 Containment 分离。
  2. 应用层 Permission 与 OS Sandbox Policy 使用同一语义来源。
  3. 用 Sandbox 换取更少审批和更高 autonomy。
  4. 优先保护 Settings、Skills、Hooks、Agent definitions 等控制平面。
  5. 把 Sandbox violation 变成结构化 Observation。
  6. 考虑执行后宿主机残留和 Git 等特殊攻击面。
  7. 为企业提供 fail-closed 模式。

十八、最终总结

Claude Code 的 Sandbox 可以定义为“嵌入 Bash Tool Runtime 的 OS 级能力约束层”。Tool Runtime 与 Permission 决定动作是否允许；shouldUseSandbox() 决定当前 Bash 是否进入隔离；sandbox-adapter.ts 把 Settings、Permission、cwd、Worktree 和网络策略转换为 SandboxRuntimeConfig；Shell.ts 再通过 @anthropic-ai/sandbox-runtime 进入具体 OS 后端。Claude Code 当前正式产品路径是 macOS Seatbelt 与 Linux/WSL2 Bubblewrap；Windows 用户通过 WSL2 使用。底层 sandbox-runtime 已提供原生 Windows alpha，通过独立 srt-sandbox SID、restricted token/Job Object、NTFS ACL/ACE 和 WFP 出站 fence 实现隔离，但这不等于 Claude Code 已正式支持 native Windows Sandbox。无论哪种后端，核心目标都是让整个进程树继承文件和网络边界，并把违规转换成可解释 Observation，与 Permission、Path Validation、Settings、REPL UI、Git Worktree 和 Tool Runtime 共同形成 defense-in-depth。
