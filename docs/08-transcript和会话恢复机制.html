Claude Code 的 Transcript 与会话恢复：从 JSONL 写入、Leaf 识别到有效分支重建

核心结论：Claude Code 的 Transcript 不是普通聊天历史，也不是长期语义 Memory，而是一个按 Session 持久化的 append-only JSONL 会话事件日志。它保存的是“节点 + 父指针 + 运行元数据”，而不是直接保存“当前 Leaf”或“当前 Branch”。恢复时，Runtime 会重新构造 Conversation Graph，修复 Compact/Snip/Progress 等结构变化，再重新计算 Leaf，选出最新的 non-sidechain Leaf 作为主会话 tip，沿 parentUuid 反向追溯并补齐并行 Tool Result，最后经过协议清洗后重新注入新的 QueryEngine。

一、Transcript 是什么？

1.1 定义

Transcript 可以理解为：

Session-scoped
Append-only
Durable
Conversation / Execution Event Log

它记录一个 Agent Session 中真正发生过的、未来可能影响恢复的事实：

  • User message
  • Assistant message
  • tool_use / tool_result
  • System / Attachment
  • Compact Boundary / Summary metadata
  • 部分 Session / Agent / Skill 状态

1.2 它不是什么？

机制回答的问题
Transcript“这个 Session 发生过什么？”
Auto Memory“以后哪些经验值得长期记住？”
CLAUDE.md“这个项目/用户要求 Claude 遵守什么？”
SessionMemory“当前长任务已经进行到哪里？”
因此：Transcript 是恢复性记忆，而不是长期语义记忆。

二、为什么使用 JSONL，而不是一个大 JSON？

Transcript 采用类似：

session-id.jsonl

entry 1
entry 2
entry 3
entry 4
...

而不是：

{
  "messages": [...]
}

这种 append-only 结构的直接收益：

  • 每产生一条新状态就能追加，不需要重写完整 Session。
  • 进程异常退出时，已经写入的前半段仍然有效。
  • 长时间 Tool Loop 下写入成本低。
  • 适合增量同步、Resume 与 Remote Bridge。
  • 天然保留历史分支，而不是覆盖旧状态。

设计思想接近简化版 Event Sourcing：

Runtime State
   ↓
Append Durable Event
   ↓
Process Exit
   ↓
Replay / Rebuild

三、运行时是怎样写 Transcript 的？

3.1 User Message 先落盘，再进入 Claude API

Claude Code 有一个非常重要的可靠性顺序：

User submit
   ↓
processUserInput()
   ↓
mutableMessages.push(...)
   ↓
recordTranscript(...)
   ↓
Claude API

而不是：

User
 ↓
Claude API
 ↓
等待 Assistant
 ↓
最后才写 Transcript

这样即使 API 首个响应前进程 crash / Ctrl+C，刚刚提交的用户请求已经成为 durable state。

3.2 Tool Loop 也持续追加

User
 ↓
Assistant: tool_use Read
 ↓
tool_result
 ↓
Assistant: tool_use Edit
 ↓
tool_result
 ↓
Assistant: tool_use Bash
 ↓
tool_result
 ↓
Assistant final

这些影响后续 Agent Context 的事件都会持续写入 Transcript。

四、JSONL 里到底怎么表示 Conversation？

4.1 核心不是数组顺序，而是 uuid + parentUuid

一条 Conversation Message 概念上类似：

{
  type: "assistant",
  uuid: "A2",
  parentUuid: "U2",
  timestamp: "...",
  isSidechain: false,
  ...
}

所以真正保存的是：

uuid       = node identity
parentUuid = edge to parent

而不是：

branchId
leaf=true
currentBranch=...

4.2 正常线性对话

U1
 ↓
A1
 ↓
U2
 ↓
A2

JSONL 近似：

U1 parent=null
A1 parent=U1
U2 parent=A1
A2 parent=U2

4.3 Fork 如何自然产生？

当用户 rewind 后从旧节点重新继续：

        U2 → A2
       /
U1 → A1
       \
        U3 → A3

JSONL 只需让两个新节点拥有同一个 parent：

U2.parentUuid = A1
U3.parentUuid = A1

因此 Branch 是从 Graph 拓扑中自然推导出来的，不需要单独 Branch Table。

五、为什么 JSONL 行顺序不能直接当 Conversation 顺序？

假设写入顺序：

1 U1
2 A1
3 U2
4 A2
5 U3
6 A3

如果只按文件顺序读取，会误以为：

U1 → A1 → U2 → A2 → U3 → A3

但真实 Graph 是：

            U2 → A2
           /
U1 → A1
           \
            U3 → A3

因此恢复必须基于 parentUuid，而不是 line number。

六、Leaf 是怎么存的？答案是：根本不直接存

Leaf 是恢复时重新计算出来的。

定义：

Leaf
=
没有被任何其他 Message 的 parentUuid 指向的节点

例如：

            U2 → A2
           /
U1 → A1
           \
            U3 → A3

全部节点：

{U1, A1, U2, A2, U3, A3}

被作为 parent 引用的节点：

{U1, A1, U2, U3}

所以：

leafs = allNodes - referencedParents

      = {A2, A3}

七、为什么不能 Parse 完 JSONL 后马上计算 Leaf？

因为磁盘上的原始 Graph 可能经过：

  • Compact
  • Snip
  • Preserved Segment
  • 旧版 Progress 节点
  • Context Collapse

这些操作可能导致某些 parentUuid 需要逻辑修复。

恢复流程更接近：

parse JSONL
    ↓
Map<UUID, Message>
    ↓
legacy progress bridging
    ↓
applyPreservedSegmentRelinks()
    ↓
applySnipRemovals()
    ↓
recomputeLeaves()

7.1 Snip 为什么需要 Relink？

原来：

A → B → C → D

Snip 删除 B、C 后，如果什么都不做：

D.parentUuid = C
但 C 已不存在

链就断了。

所以恢复时需要：

D
 ↓
C deleted
 ↓
B deleted
 ↓
A survives

最后改成：

D.parentUuid = A

之后再计算 Leaf。

八、多个 Leaf 时，怎样识别主会话的有效分支？

核心策略分三步：

8.1 第一步：必须是真 Leaf

leafUuids.has(message.uuid)

不是 leaf 的节点即使 timestamp 新，也不能作为当前 branch tip。

8.2 第二步：排除 Sidechain

if (message.isSidechain)
    continue

Subagent / sidechain 可能拥有自己的最新 Leaf，但不应被当成主 Conversation。

8.3 第三步：剩余 Main Leafs 中选 timestamp 最新的

for each message:
    if is leaf
       and !isSidechain
       and timestamp > currentTipTimestamp
    then:
       tip = message

因此当前主分支 tip 的基本定义是：

Newest non-sidechain leaf

九、用完整 Fork 示例看有效分支选择

JSONL：

U1  parent=null   10:00
A1  parent=U1     10:01

U2  parent=A1     10:02
A2  parent=U2     10:03

U3  parent=A1     10:10
A3  parent=U3     10:11

Graph：

            U2 → A2  (leaf, 10:03)
           /
U1 → A1
           \
            U3 → A3  (leaf, 10:11)

候选：

A2
A3

两者都不是 sidechain，因此比较时间：

A2 = 10:03
A3 = 10:11

最终：

tip = A3

旧分支：

U2 → A2

仍然保留在 JSONL，但不属于当前恢复的主链。

十、选出 Tip 后怎么重建 Conversation Chain？

核心思想：

tip
 ↓
parentUuid
 ↓
parentUuid
 ↓
...
 ↓
root

例如：

A3.parentUuid = U3
U3.parentUuid = A1
A1.parentUuid = U1
U1.parentUuid = null

先得到：

A3
U3
A1
U1

最后 reverse：

U1
 ↓
A1
 ↓
U3
 ↓
A3

这就是当前主 Conversation Chain。

十一、为什么 Parent Walk 还不够？并行 Tool Call 的特殊问题

Claude 可能一次生成多个：

tool_use Read A
tool_use Read B
tool_use Grep C

Streaming / Tool Result 落盘后，多个 sibling 结果可能不全部位于同一条简单 parent 链中。

因此：

buildConversationChain()
    ↓
parentUuid backward walk
    ↓
reverse
    ↓
recoverOrphanedParallelToolResults(...)

恢复器还需要补回在 parallel tool use 场景中可能遗漏的 sibling Tool Result。

所以：Conversation Recovery 不是单纯的 linked-list traversal，而是“主链回溯 + 并行 Tool sibling 修补”。

十二、为什么有效 Branch 还不一定能直接发给 Claude API？

Graph 上合法，不等于 Protocol 上合法。

可能存在：

  • 未完成的 tool_use
  • 孤立 thinking
  • 空 assistant message
  • 中断在 Tool Call 中间的 Turn

因此恢复还需要：

Graph-valid chain
    ↓
deserializeMessages()
    ↓
filter unresolved tool_use
    ↓
filter orphan thinking
    ↓
repair interrupted turn
    ↓
Runtime-valid Messages

最终才可以重新进入 QueryEngine / Claude API。

十三、ToolUse / ToolResult 为什么是恢复不变量？

Claude Messages API 需要：

tool_use.id
      ↕
tool_result.tool_use_id

如果 Transcript 停在：

Assistant:
tool_use id=toolu_123

CRASH

那么直接 Resume 会形成非法对话。

因此恢复器必须识别：

unresolved tool_use
```

并做过滤/修复，保证重新注入模型时协议成立。



十四、Compact 与 Transcript 的关系



14.1 RAM 和 Durable History 是两套状态



Compact 前：



QueryEngine.mutableMessages
=
大量原始历史




Compact 后：



QueryEngine.mutableMessages
=
summary / compact boundary 后 active messages




但 Transcript 仍可保留：



旧 durable history
+
compact metadata
+
new history




所以：



Transcript
= Durable full/session history

mutableMessages
= Active working context




14.2 Resume 时为什么要识别最新 Compact Boundary？



超长 Transcript 不必完整恢复到 Active Context。Loader 可以优先定位最新 Compact Boundary，从那里恢复当前有效上下文，同时单独扫描边界前仍需要的 Session Metadata。



十五、Progress / Legacy Entry 为什么也会影响 Leaf？



旧版结构中，某些真实消息的 parentUuid 可能曾经指向 Progress Entry。



但 Progress 并不是 durable conversation node。



所以恢复时需要类似：



Real Message
    ↓
parent = old progress node
    ↓
progress bridge
    ↓
real parent




否则主链会在历史 Progress 节点处断掉。



十六、Subagent / Sidechain 怎么避免污染主会话？



Claude Code 通常还会在物理存储上把主 Session 与 Subagent Sidechain 分开：



session-id.jsonl

session-id/
└─ subagents/
   ├─ agent-A.jsonl
   └─ agent-B.jsonl




逻辑上又有：



isSidechain




因此是两层保护：



Storage namespace isolation
        +
Logical sidechain filtering




这样 Resume 主 Session 时不会因为某个 Subagent 时间戳更新就错误选择它的 Leaf。



十七、Transcript 与 FileHistory 为什么必须一起看？



Transcript 只解决 Conversation State。



假设：



Turn 1: 改 a.ts
Turn 2: 改 b.ts
Turn 3: 改 c.ts




如果用户 rewind 到 Turn 1，仅恢复 Transcript：



Claude 认知：
只改过 a.ts

真实磁盘：
a.ts
b.ts
c.ts
都已经修改




于是：



Cognitive State
≠
World State




所以：



Transcript
= Conversation State Recovery

FileHistory
= Workspace State Recovery




真正的 Coding Agent Resume/rewind 需要二者配合。

十九、为什么 Transcript 不直接存 Current Branch / Leaf？



这种设计有几个明显好处：



    

  • Append-only，不需要回头修改旧记录。
    • 

  • Fork / rewind 不会破坏旧分支。
    • 

  • 恢复逻辑可以兼容 Compact、Snip、Legacy Progress 等结构变化。
    • 

  • 旧分支保留，未来可以审计、恢复或做分支选择。
    • 

  • 避免“某次 branch pointer 写入失败”导致整个会话不可恢复。
    • 




代价是：



    

  • 读取侧复杂度显著提高。
    • 

  • 必须重建 Graph。
    • 

  • 必须重新计算 Leaf。
    • 

  • 必须处理并行 Tool / Compact / Snip / Sidechain / Legacy migration。
    • 




所以 Claude Code 的 Transcript 设计明显属于：



Write path simple，Read/Recovery path sophisticated。



二十、最关键的源码理解





问题答案


Leaf 存在哪里？不直接存；恢复时根据 Graph 重算。


Branch 如何表示？多个 Message 共享同一 parentUuid。


当前主 Branch 怎么选？从 Leaf 中排除 sidechain，通常选 timestamp 最新者。


Branch 怎么重建？从 tip 沿 parentUuid 反向走到 root，再 reverse。


并行 Tool 怎么处理？主链构建后补 sibling/orphaned parallel tool results。


Compact/Snip 怎么处理？先 relink/repair Graph，再 recompute leaf。


恢复后能直接发 API 吗？不能；还需协议级 sanitize。


Workspace 怎么恢复？配合 FileHistory，而不是只靠 Transcript。

二十二、与 Agent Harness 设计的关系



如果自己实现 Agent Harness，Claude Code 这套机制至少给出 5 个很强的工程启发：



    

  1. Transcript 应保存 Durable Facts，不要序列化 Runtime Object。
    2. 

  2. Append-only 写入比频繁覆盖 Session Snapshot 更抗 crash。
    3. 

  3. 分支关系用 Parent Pointer 表达，比单独维护 Branch Table 更自然。
    4. 

  4. Active Branch 应从 Graph 推导，而不是依赖“最后一行”。
    5. 

  5. 恢复必须分成 Graph Repair → Branch Selection → Protocol Repair → Runtime Rehydration 四步。
    6.

二十四、一句话总结





Claude Code 的 Transcript 是一个按 Session 追加写入的 JSONL durable event log。它不直接存 Leaf 或 Active Branch，而是为每条 Conversation Message 保存 uuid 与 parentUuid，由多个节点共享同一个 parent 自然表达 Fork；恢复时先重建 Message Graph，并处理 Progress、Compact、Preserved Segment、Snip 等链路修复，再把“未被任何其他 Message 的 parentUuid 引用”的节点重新计算为 Leaf；多个 Leaf 中排除 isSidechain，通常选择 timestamp 最新的 non-sidechain Leaf 作为主 Conversation tip；随后从 tip 沿 parentUuid 反向追溯到 Root、reverse 成正向消息链，补齐并行 Tool Result，再过滤 unresolved tool_use、orphan thinking 和中断状态，最后把恢复出的合法 Messages、Session Metadata、Skill/FileHistory/Compact 状态重新注入新的 QueryEngine。它本质上是一套“append-only log + conversation graph reconstruction + runtime rehydration”的会话恢复机制。
