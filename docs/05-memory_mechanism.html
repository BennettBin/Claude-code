BennettBin/Claude-code · Category-first Memory Architecture

Claude Code 的记忆机制：按记忆类别拆解，并追踪一次完整会话的存储与调用

这版先按“记忆是什么”来拆，而不是按源码目录来拆。Claude Code 的记忆可以分成 6 类：①运行时工作记忆；②静态指令记忆；③会话摘要记忆；④跨会话长期记忆；⑤作用域专属记忆（Agent/Team）；⑥恢复性记忆（Transcript/FileHistory）。其中只有第④类最接近通常所说的“长期语义记忆”；第⑥类负责恢复，不负责语义召回。一次真实会话会同时使用其中多类，而不是只访问一个 Memory Store。

源码边界：本文基于 BennettBin/Claude-code 恢复源码。仓库 README 自身说明：这是从公开发布物 source map 恢复出的 TypeScript 源码树，版本标记为 999.0.0-restored，不是 Anthropic 官方开发仓库。文中凡涉及 Feature Gate、Remote Config、Team Memory、AutoDream 等条件能力，都按“源码中存在且满足 gate 时启用”描述。

一、先看全景：6 类记忆分别解决什么问题？

类别核心问题主要存储生命周期主要读取时机
A. 运行时工作记忆 “这一轮/这个会话已经发生了什么？” RAM：QueryEngine.mutableMessages、readFileState、ToolUseContext 当前进程/Conversation 每次 queryLoop / Tool 调用
B. 静态指令记忆 “Claude 在这个用户/项目/目录里应该遵守什么？” CLAUDE.md、rules、local memory 长期文件 Session 启动 + 进入嵌套目录时
C. 会话摘要记忆 “长任务现在做到哪里，Compact 后如何继续？” SessionMemory Markdown notes 当前 Session 长会话中后台更新；Compact 时使用
D. 跨会话长期记忆 “以后还值得记住什么？” MEMORY.md + topic .md 跨 Session 每次新会话入口加载 + 每轮按需召回
E. 作用域专属记忆 “哪些经验只属于某类 Agent 或某个团队？” Agent Memory / Team Memory 目录 跨 Session，按 scope Agent 启动 / Team Memory 注入与召回
F. 恢复性记忆 “进程退出后，怎样恢复到此前会话/代码状态？” Transcript JSONL、Compact metadata、FileHistory Session durable /resume、rewind、故障恢复
最重要的区分：
Auto Memory 解决“跨会话语义记忆”；
SessionMemory 解决“当前长会话摘要”；
Transcript 解决“会话事件恢复”；
CLAUDE.md 解决“人工确定的长期规则”。
四者绝不是同一种 Memory。

二、A 类：运行时工作记忆（Working Memory）

2.1 核心载体是 QueryEngine

恢复源码中的 src/QueryEngine.ts 明确把 QueryEngine 设计成一个 Conversation 级对象。它不是“一次 API 请求一个对象”，而是在同一会话里跨多次 submitMessage() 保留状态。

QueryEngine
├─ mutableMessages
├─ readFileState
├─ totalUsage
├─ permissionDenials
├─ abortController
├─ discoveredSkillNames
└─ loadedNestedMemoryPaths

2.2 mutableMessages 是短期记忆主体

它保存当前模型下一次请求需要看到的消息链，包括：

User
Assistant
Tool Result
System / Attachment
Compact Boundary 后仍保留的 active messages

典型 ReAct 循环：

User: 修复 bug
    ↓
mutableMessages += User
    ↓
Claude → tool_use Read
    ↓
Read result
    ↓
mutableMessages += tool_result
    ↓
Claude → tool_use Edit
    ↓
Edit result
    ↓
mutableMessages += tool_result
    ↓
Claude final

这里的 Tool Result 就是 Observation，也是下一次模型推理的工作记忆。

2.3 readFileState 是“对文件世界的认知记忆”

Claude Code 不只需要知道“对话里提过某文件”，还需要知道 Agent 最近实际读取过哪些文件状态。这个状态用于避免 Edit 建立在未知或过期内容上。

Read(foo.ts)
    ↓
readFileState 记录观察状态
    ↓
Edit(foo.ts)
    ↓
Runtime 判断该 Edit 是否建立在有效读取上

2.4 loadedNestedMemoryPaths 是 Session 级去重记忆

当 Tool 进入某个更深目录时，可能发现局部 CLAUDE.md。该文件被作为 nested_memory attachment 注入后，路径会加入 loadedNestedMemoryPaths。这个 Set 跨 Turn 保留，用来防止同一局部指令反复注入。

Read src/service/foo.ts
    ↓
发现 src/service/CLAUDE.md
    ↓
注入 nested_memory
    ↓
loadedNestedMemoryPaths.add(path)
    ↓
后续 Turn 再访问该目录
    ↓
不重复注入

2.5 运行时工作记忆什么时候消失？

进程结束后 RAM 状态消失。因此它如果要被恢复，必须依靠 F 类“恢复性记忆”中的 Transcript / FileHistory 等 Durable State 重新水合。

三、B 类：静态指令记忆（CLAUDE.md / Rules）

3.1 它存的不是“对话经验”，而是稳定规则

src/utils/claudemd.ts 所体现的是人工维护的 Instructions Memory。典型内容：

  • 编码规范。
  • 架构边界。
  • 测试命令。
  • 禁止事项。
  • 某目录特殊约束。

3.2 主要作用域

作用域语义
Managed企业管理员强制规则。
User用户跨项目通用规则。
Project项目共享规则，如项目根或 .claude/ 下的 CLAUDE.md/rules。
Local只对当前机器/本地工作区有效、不一定进入版本控制的规则。

3.3 两种加载模式

启动时：Eager load

Session start
    ↓
发现 managed/user/project/local CLAUDE.md
    ↓
加入 Context Construction

运行中：Lazy nested load

Agent 进入更深目录
    ↓
发现该目录局部 CLAUDE.md
    ↓
nested_memory attachment
    ↓
记录 loadedNestedMemoryPaths

3.4 为什么它不属于 Auto Memory？

因为 CLAUDE.md 代表用户/组织明确声明的规范。它不应该被后台总结 Agent 自动改写或和概率性的“学到的偏好”混在一起。

四、C 类：会话摘要记忆（SessionMemory）

4.1 目标：保持“继续工作的能力”

src/services/SessionMemory/ 维护的是当前长会话的结构化笔记，不是跨会话用户画像。

SessionMemory
≈ Current Task Continuation Brief

典型模板包含：

  • Session Title
  • Current State
  • Task Specification
  • Files and Functions
  • Workflow
  • Errors & Corrections
  • Codebase/System Documentation
  • Learnings
  • Key Results
  • Worklog

4.2 什么时候开始维护？

恢复源码中的默认阈值是：

首次初始化：
minimumMessageTokensToInit ≈ 10,000 tokens

后续更新：
minimumTokensBetweenUpdate ≈ 5,000 tokens

并通常要求：
toolCallsBetweenUpdates ≈ 3

如果 Token 已达到更新阈值且当前出现自然停顿（最后一轮没有工具调用），也可以更新，而不必机械等到 3 个 Tool Call。

4.3 谁来写？

不是主 Agent 一边正常工作一边自己总结，而是：

Main Agent messages
    ↓
SessionMemory trigger
    ↓
runForkedAgent()
    ↓
专用 SessionMemory 子 Agent
    ↓
只允许修改对应 Session Memory file

这个后台 Agent 权限非常窄，主要只允许 Edit 那个会话笔记文件，避免一个“总结任务”拥有修改代码或执行 Bash 的能力。

4.4 为什么它和 Compact 紧密绑定？

当 Context Window 变长时，Runtime 不需要临时重新读取全对话再做昂贵总结，而可以复用已经持续维护的 SessionMemory。

长会话持续运行
    ↓
后台 SessionMemory 已不断维护
    ↓
Context 接近阈值
    ↓
sessionMemoryCompact
    ↓
把高密度 Session Notes 作为 Compact 基础

所以 SessionMemory 更接近“会话级滚动摘要缓存”。

五、D 类：跨会话长期记忆（Auto Memory）

5.1 这是最接近通常意义上的 Long-Term Memory

核心目录是 src/memdir/。默认物理布局大致：

~/.claude/
└─ projects/
   └─ <sanitized-canonical-git-root>/
      └─ memory/
         ├─ MEMORY.md
         ├─ user_role.md
         ├─ feedback_testing.md
         ├─ project_release.md
         └─ reference_dashboard.md

源码使用 canonical Git root 作为项目 identity，因此同一 repository 的多个 worktree 可以共享同一 Auto Memory。

5.2 MEMORY.md 是索引，不是完整正文

MEMORY.md
    ↓
简短入口 / pointers

topic files
    ↓
详细长期记忆正文

源码限制入口文件大致为：

MAX_ENTRYPOINT_LINES = 200
MAX_ENTRYPOINT_BYTES = 25,000

设计目的是让每次 Session 启动时可以加载一个小而稳定的长期记忆入口，而不是每轮把整个长期记忆目录塞进 Context。

5.3 长期记忆内部再分 4 个语义类别

类型应该保存什么例子
user用户角色、目标、长期偏好、专业背景。“用户希望解释偏工程化而不是产品宣传。”
feedback用户对 Claude 工作方式的纠正、确认和方法偏好。“测试不能使用 DB mock。”
project无法仅从代码重新推导的重要项目事实/决策。“下一版本必须保持 API backward-compatible。”
reference外部资源的稳定定位信息。“生产监控入口在哪里。”

5.4 什么不应该存进长期记忆？

Memory Extraction Prompt 刻意排除：

  • 当前代码直接能重新读取出来的普通事实。
  • Git 历史本身已有的信息。
  • 一次性 Debug 中间过程。
  • 短暂任务状态。
  • CLAUDE.md 已经明确记录的规则。

基本原则是：

只保存“未来仍有价值，而且无法低成本从当前世界重新推导”的信息。

六、D 类记忆怎么召回：不是 Vector DB，而是两阶段选择

6.1 第一阶段：廉价 Manifest Scan

memoryScan.ts 会扫描 topic markdown，而不是直接读取所有全文。

memory/*.md
    ↓
最多扫描约 200 个文件
    ↓
只读取 Frontmatter / Header
    ↓
filename
name
description
type
mtime

Frontmatter 只需承担“可检索摘要”的职责。

6.2 第二阶段：Side Query 语义选择

当前用户请求
+
Memory manifest
+
recent tools / already surfaced
    ↓
findRelevantMemories()
    ↓
Side Query（恢复源码中使用 Sonnet 级 selector）
    ↓
选择最多少量相关 topic files（典型最多 5）
    ↓
读取正文
    ↓
relevant_memories attachment
    ↓
Main Agent Context

6.3 为什么不用 embedding/vector DB？

这套实现的工程取舍是：

  • 文件可读、可编辑、可备份。
  • 不需要 embedding index lifecycle。
  • 小型 manifest 足够便宜。
  • LLM selector 可以直接理解 description 和当前任务。

6.4 已经召回过的文件不会反复占槽位

alreadySurfaced 会在 Session 内去重。否则一个总是相关的 topic file 可能每轮都重复占用有限的相关记忆槽位。

6.5 Memory 有 Freshness，不被当成实时事实

memoryAge.ts 会基于修改时间生成 stale warning。长期记忆中的 file path、line number、代码行为都可能过期，因此模型会被提醒重新验证当前代码。

七、D 类记忆怎么写入：主 Agent + 后台 Extractor + AutoDream

7.1 主 Agent 可以主动保存

当用户明确要求记住，或模型根据 Memory Prompt 判断某条信息非常值得长期保留时，可以直接维护 topic file 和 MEMORY.md。

7.2 后台 extractMemories 是“忘记保存”的兜底

完整 Query Loop 结束
模型已经给出最终回答
且没有后续 tool_use
    ↓
Stop Hooks
    ↓
extractMemories
    ↓
Forked Agent
    ↓
只分析尚未处理的新消息区间
    ↓
必要时写 Auto Memory

提取 Agent 权限遵循最小权限：

Tool权限
Read / Grep / Glob允许读取。
只读 Bash有限允许。
Edit / Write只允许 Auto Memory 目录。
其他高风险 Tool拒绝。

7.3 如果主 Agent 已经写了 Memory，Extractor 会跳过

源码通过类似 hasMemoryWritesSince() 的逻辑避免：

Main Agent 写 memory
        +
Background Extractor 又写同一内容
        ↓
重复 / 冲突

7.4 AutoDream 是低频 Consolidation

长期运行后记忆目录可能出现重复、冲突、过时内容。AutoDream 的作用更像：

多个 Session 的增量记忆
    ↓
低频后台整理
    ↓
merge
dedupe
remove stale/conflict
rewrite index

因此：

extractMemories = 记笔记
autoDream       = 整理笔记本

八、E 类：作用域专属记忆（Agent Memory / Team Memory）

8.1 Agent Memory：每类 Agent 自己的经验

src/tools/AgentTool/agentMemory.ts 把 Agent Memory 分为：

Scope典型路径作用
user~/.claude/agent-memory/<agent-type>/某 Agent 类型跨项目经验。
project.claude/agent-memory/<agent-type>/该 Agent 在项目里的共享经验。
local.claude/agent-memory-local/<agent-type>/只对本机环境有效的经验。

例如 Explore Agent 的代码导航经验，没有必要写进用户主 Auto Memory。

8.2 Team Memory：团队共享知识空间

Team Memory 与私人 Auto Memory 分开，并有独立同步逻辑。源码中此能力受 Feature Gate/配置控制，所以它是条件能力。

Private Auto Memory
    ↓
用户私有经验

Team Memory
    ↓
可以跨团队成员同步的项目级知识

这样避免把私人偏好与组织共享规则混为一体。

九、F 类：恢复性记忆（Transcript / Compact / FileHistory）

9.1 Transcript 不是语义长期记忆

它解决的是：

“这个 Session 到底发生了什么？”

而不是：

“未来哪些经验应该被召回？”

9.2 Transcript 是 JSONL 式 durable event log

运行时会持续记录 User、Assistant、Tool interaction、System/Attachment、Compact metadata 等。一个关键可靠性设计是：

User submit
    ↓
mutableMessages.push()
    ↓
recordTranscript()
    ↓
再调用 Claude API

即用户请求先落盘，再进入模型调用，避免 API 首个响应前进程退出导致刚提交的用户请求丢失。

9.3 Compact Boundary 连接“RAM Working Memory”和“Durable History”

Compact 前：
RAM = 大量历史消息
Disk = 完整 transcript

Compact 后：
RAM = summary / boundary 后 active messages
Disk = 旧历史 + compact metadata + 新历史

所以 Compact 可以释放 RAM/Context，但不意味着过去的 Session durable history 被抹掉。

9.4 FileHistory 负责恢复 World State

仅恢复 Conversation 不够：

对话恢复到 T1
但磁盘还停留在 T5
    ↓
Agent Cognitive State ≠ Workspace State

FileHistory / snapshot 机制让 rewind/恢复可以同时协调文件状态。

9.5 conversationRecovery.ts 负责 Runtime Rehydration

Transcript
    ↓
loadConversationForResume()
    ↓
重建合法消息链
    ↓
处理未完成 tool_use / orphan thinking
    ↓
恢复 Skill state
    ↓
复制/恢复 FileHistory
    ↓
initialMessages
    ↓
新的 QueryEngine

这说明 Claude Code 恢复的是durable facts，而不是序列化整个 QueryEngine 对象。

十、现在把 6 类记忆串起来：一次完整会话发生了什么？

阶段 0：新会话启动——先装入“长期背景”

假设用户进入一个 Git 项目后启动 Claude Code。

Claude Code startup
    ↓
识别 cwd / project / canonical git root
    ↓
加载 B 类静态指令记忆
    ├─ Managed CLAUDE.md
    ├─ User CLAUDE.md
    ├─ Project CLAUDE.md / rules
    └─ Local rules
    ↓
定位 D 类 Auto Memory directory
    ↓
读取 MEMORY.md 入口索引
    ↓
创建 QueryEngine
    ↓
A 类 Working Memory 初始为空/由恢复消息初始化

此时模型还没有看到全部 topic memory 正文；它只拥有稳定入口和其它基础 Context。

阶段 1：用户提交第一条请求

用户输入：

“帮我运行测试并修复失败项。”

发生：

processUserInput()
    ↓
User Message
    ↓
A 类：
mutableMessages += user
    ↓
F 类：
recordTranscript(user)
    ↓
D 类：
启动 relevant-memory selection / prefetch
    ↓
Context Construction
    ├─ CLAUDE.md
    ├─ MEMORY.md
    ├─ relevant topic memories（若匹配）
    └─ current messages
    ↓
Claude API

阶段 2：长期记忆按当前请求进行“选择性召回”

假设长期记忆目录里已有：

feedback_testing.md
description:
“Project tests must use pnpm test; npm test is unsupported.”

Recall 流程：

User query: “运行测试”
    ↓
scan memory headers
    ↓
build manifest
    ↓
sideQuery selector
    ↓
选中 feedback_testing.md
    ↓
读取正文
    ↓
relevant_memories attachment
    ↓
Claude 得知应该使用 pnpm test

这就是跨会话长期记忆真正“调用”的时刻。

阶段 3：Claude 开始 Tool Loop——工作记忆不断增长

Claude
  → Bash("pnpm test")
        ↓
Tool Result
        ↓
A 类：
mutableMessages += observation
        ↓
F 类：
Transcript += tool interaction
        ↓
Claude
  → Read("src/foo.ts")
        ↓
readFileState 更新
        ↓
如果进入新子目录并发现 CLAUDE.md
        ↓
B 类 nested instruction memory 注入
        ↓
loadedNestedMemoryPaths 去重

这一阶段主要依赖 A 类 Working Memory，B/D 类只在需要时提供稳定背景。

阶段 4：会话越来越长——SessionMemory 开始维护 continuation brief

当上下文达到大约 10K Token 以上，并满足后续更新阈值：

A 类完整消息历史
    ↓
SessionMemory trigger
    ↓
Forked summary agent
    ↓
C 类 SessionMemory file
    ↓
记录：
Current State
Files
Workflow
Errors
Learnings
Worklog

之后每增长一段有效上下文再增量更新，而不是每轮重新生成整份摘要。

阶段 5：Context Window 压力增大——分层 Compact

Context growing
    ↓
优先 Microcompact
    ├─ 清理旧的大 Tool Result
    ↓
仍接近阈值
    ↓
SessionMemory Compact
    ├─ 利用 C 类滚动工作简报
    ↓
必要时 Full/Reactive Compact
    ↓
生成 compact boundary / summary
    ↓
A 类 RAM 工作记忆缩小
F 类 Transcript 保留 durable boundary/history

这里发生的不是“遗忘全部过去”，而是：

高成本原始细节
    → 移出 Active Context

高价值任务状态
    → 通过 SessionMemory / Summary 继续保留

阶段 6：一轮完整任务结束——把“值得以后记住的东西”写入长期记忆

假设在本次对话中用户明确纠正：

“以后这个项目不要用 npm test，只能用 pnpm test。”

这一信息先进入：

A 类 mutableMessages
F 类 Transcript
C 类 SessionMemory（若已启用）

当完整 Query Loop 结束：

Final assistant response
    ↓
Stop Hooks
    ↓
检查主 Agent 是否已经主动写 Auto Memory
    ├─ 已写 → extractor 跳过该区间
    └─ 未写
         ↓
      extractMemories
         ↓
      Forked memory agent
         ↓
      判断它属于 feedback
         ↓
      写：
      feedback_testing.md
         ↓
      更新 MEMORY.md index

这一步才真正把一个“本会话出现的信息”转化成“下次会话可召回的长期记忆”。

阶段 7：Session 结束——哪些东西留下，哪些消失？

内容退出后
mutableMessages / ToolUseContextRAM 消失。
CLAUDE.md文件继续存在。
SessionMemory file对应 Session 的笔记文件继续存在，供该会话生命周期/Compact 机制使用。
Auto Memory长期存在，下次项目会话继续使用。
Agent/Team Memory按其 scope 长期存在。
Transcript/FileHistory继续作为该 Session 的恢复材料。

阶段 8A：用户 Resume 同一个 Session

/resume
    ↓
F 类 Transcript
    ↓
session discovery
    ↓
loadConversationForResume()
    ↓
repair protocol invariants
    ├─ unresolved tool use
    ├─ orphan thinking
    └─ compact-related state
    ↓
restore invoked skill state
    ↓
copy / restore FileHistory
    ↓

    ↓

    ↓

与此同时，项目的 CLAUDE.md 与 Auto Memory 仍属于当前 Runtime 的长期背景来源。Resume 的核心区别在于：Transcript 负责恢复“这个 Session 发生过什么”。

十五、这套 Memory Architecture 的核心设计原则

  1. 确定性规则与概率性学习分开。CLAUDE.md ≠ Auto Memory。
  2. Working Memory 与 Durable Memory 分开。RAM 为性能，Transcript 为恢复。
  3. Session Summary 与 Cross-session Learning 分开。SessionMemory ≠ Auto Memory。
  4. Index 与正文分开。MEMORY.md 小而稳定，Topic files 按需读取。
  5. Recall 与 Storage 分开。存很多并不代表每轮都注入很多。
  6. 按作用域隔离。User / Project / Local / Agent / Team 不混成一个 namespace。
  7. Memory 要考虑 freshness。长期记忆不是实时数据库。
  8. 自动写入使用最小权限。后台 Memory Agent 不能随便改代码或执行副作用 Tool。
  9. Recovery 恢复事实而不是 Runtime Object。新的 QueryEngine 从 Durable State 重新构造。
  10. Cognitive State 与 World State 一起恢复。Transcript + FileHistory 配套。

十八、一句话总结

Claude Code 不是“短期 Memory + 长期 Memory”两层结构，而是按职责拆成 6 类：QueryEngine 提供 RAM 工作记忆；CLAUDE.md 提供确定性静态指令；SessionMemory 保存当前长会话的滚动工作摘要；memdir 的 MEMORY.md + topic files 保存跨会话长期经验并按语义选择性召回；Agent/Team Memory 提供独立作用域；Transcript + Compact metadata + FileHistory 保存会话和工作区的可恢复事实。一次信息会根据价值沿不同路径流动：先进入 Working Memory，同时写 Transcript；如果会话足够长则进入 SessionMemory；如果对未来有持续价值则由 Main Agent 或 extractMemories 晋升为 Auto Memory；下一次新 Session 再通过 MEMORY.md + manifest + side-query 召回，而同一 Session 的 Resume 则走 Transcript Rehydration。理解这条“存储—提炼—压缩—召回—恢复”流水线，比把源码模块逐个列出来更接近 Claude Code 真正的 Memory Architecture。
