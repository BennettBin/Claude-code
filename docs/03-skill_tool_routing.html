Claude Code 中 Skill 与 Tool：关系、选择机制与 PPT 生成案例

本文结合 BennettBin/Claude-code 恢复源码，系统说明 Skill 与 Tool 的结构关系、各自职责，以及 Claude 如何判断是直接使用原子 Tool，还是先调用 Skill；最后通过“PPT 生成”给出一条完整端到端调用链。

核心结论：Tool 是可执行的原子能力；Skill 是可复用的过程知识、工作流与运行配置。Claude Code 不是按“简单任务/复杂任务”硬分类，而是判断当前请求是否与某个 Available Skill 匹配。匹配时先调用 SkillTool，再由 Skill 指导 Agent 组合多个 Tool 完成任务。

说明：BennettBin/Claude-code 不是 Anthropic 官方开源仓库，而是依据公开发布物/source map 恢复出的源码树。

Skill 不替代 Tool，而是指导如何组合 Tool。

左侧“直接原子执行”分支实际上也不是模型调用一个 Tool 后就直接进入 tool.call()。 它会完整经过 Claude Code 的 Tool Runtime：Tool 查找、Schema 校验、Tool 语义校验、 PreToolUse Hooks、Permission Resolution、真正执行、Post/Failure Hooks、结果标准化， 最后把 tool_result 回填到 messages，再进入下一轮 queryLoop()。 因此 Skill 路径与普通 Tool 路径最终都会汇入统一 Tool Runtime。

2. Tool：原子执行能力

Tool 基础抽象位于 src/Tool.ts。可以简化为：

Input
  ↓
Schema / Validation
  ↓
Permission
  ↓
call()
  ↓
Output

典型 Tool 包括 Read、Grep、Bash、Edit、MCPTool、AgentTool 和 SkillTool。

Tool 解决的是：

“现在已经决定要做某个动作，这个动作如何真正执行？”

所以 Tool 更接近：

Capability Primitive
=
可执行的原子能力

3. Skill：过程知识与复合能力

Skill 主要来自：

.claude/skills/<skill-name>/SKILL.md

加载逻辑主要位于 src/skills/loadSkillsDir.ts。Skill 被加载后更接近一个 prompt-based Command，而不是普通 Tool。

Skill 可包含：

  • name / description / whenToUse
  • 完整任务 SOP / Prompt
  • allowedTools
  • model override
  • effort override
  • hooks
  • execution context：inline / fork

Skill 解决的是：

“这类任务应该按什么流程做？
优先检查什么？
怎样组合工具？
用什么模型和 effort？
是否需要 fork 子 Agent？”
Skill 更接近 SOP + Prompt + Runtime Configuration。

4. SkillTool：Skill 与 Tool Runtime 的桥

源码中存在 src/tools/SkillTool/SkillTool.ts，其中 SkillTool 本身通过通用 Tool abstraction 构建，因此它确实是一个 Tool。

它的典型输入可概括为：

{
  "skill": "review-pr",
  "args": "123"
}

调用链：

Claude
  ↓ tool_use
SkillTool
  ↓
Skill Registry
  ↓
找到具体 Skill
  ↓
加载 SKILL.md
  ↓
展开 Prompt / Workflow

这样 Skill 就可以复用现有 Tool Runtime：

runToolUse()
  ↓
Schema Validation
  ↓
Permission
  ↓
SkillTool.call()
  ↓
tool_result

因此 SkillTool 最适合理解成一个 Meta Tool / Bridge Tool。

5. Skill 与 Tool 的核心区别

最直观的类比：Skill = SOP；Tool = 设备。

6. Claude 如何决定是 Tool 还是 Skill？

源码里没有看到一个“简单任务 → Tool；复杂任务 → Skill”的显式分类器。

真正更接近：

当前请求
   ↓
是否与某个 Available Skill 匹配？
   │
 ┌─┴─────────────┐
 │               │
Yes              No
 │               │
 ▼               ▼
SkillTool       正常 Tool Selection
 │               │
 ▼               ▼
完整 Skill      Read / Bash / Edit / ...

所以判断依据主要是：

是否存在与当前请求匹配的专用 Procedural Knowledge

简单任务也可能用 Skill

如果存在专门的 commit Skill，那么“提交当前修改”即使不复杂，也可能先走 Skill。

复杂任务也可能不用 Skill

如果没有对应 Skill，一个跨多个模块的复杂 debugging 任务仍可以直接通过很长的 Read/Grep/Bash/Edit Agent Loop 完成。

Skill ≠ 复杂任务；Tool ≠ 简单任务。

7. Skill Discovery：Claude 一开始并不会读取所有 SKILL.md

关键逻辑涉及 src/commands.ts 和 src/tools/SkillTool/prompt.ts。

getSkillToolCommands() 负责构建模型可主动调用的 Skill 候选集合；例如会考虑 prompt 类型、是否允许 model invocation 等。

Claude 一开始看到的是轻量 Skill index：

name
+
description
+
whenToUse

然后由模型做语义匹配：

User Request
      ↕
Skill name / description / whenToUse

只有选中以后才：

SkillTool("xxx")
   ↓
加载完整 SKILL.md
这是一种 Discovery → Selection → Lazy Full Loading。

这样可以显著减少大量 Skill 带来的上下文膨胀。

8. Skill 匹配后为什么要优先 Skill？

SkillTool/prompt.ts 中的使用提示明确要求模型：如果某个 Skill 与当前请求匹配，应先调用相关 Skill，再继续处理任务。

目的包括：

  1. 避免模型临时 improvisation 绕过已有 SOP。
  2. 复用组织沉淀的过程知识。
  3. 提高同类任务执行的一致性。
  4. 让 Skill 附带的 model / effort / hooks / allowed-tools 等配置生效。
有明确 Skill 匹配
     ↓
优先复用 Skill

没有 Skill 匹配
     ↓
Claude 自主规划 + 原子 Tool

9. PPT 生成案例：Skill 与 Tool 的完整选择和调用

下面的 ppt-generation Skill 是为了说明架构机制的示例，不代表仓库中必然存在同名内置 Skill。

9.1 用户请求

“帮我根据项目里的季度经营数据，
生成一份 10 页的管理层汇报 PPT，
包含关键 KPI、趋势图、风险和下季度行动计划。”

该任务包含数据读取、内容理解、结构规划、图表选择、文案生成、幻灯片创建、渲染检查和修复等多个步骤。

但 Claude 不是因为“它复杂”才调用 Skill，而是因为假设 Skill Registry 中存在一个明确匹配的 PPT Skill。

9.2 第一阶段：Skill Discovery

Claude 可能看到：

Available Skills:

ppt-generation:
Create professional presentation decks from source materials.
Use when the user asks to create, revise, structure,
or export a PowerPoint / slide presentation.

code-review:
Review code changes for correctness.

debugging:
Systematically diagnose software failures.

语义匹配：

User Request:
“生成 10 页管理层 PPT”

          ↓

ppt-generation

于是先产生：

tool_use:
Skill({
  "skill": "ppt-generation",
  "args": "Generate a 10-slide management deck from project quarterly data"
})

9.4 第三阶段：加载完整 PPT SOP

假设 Skill 内容大致为：

目标：
生成管理层汇报 PPT。

流程：
1. 识别数据源。
2. 提取最重要的 KPI。
3. 形成 10 页以内的 story arc。
4. 每页只表达一个核心信息。
5. KPI 使用大数字卡片。
6. 趋势数据优先 line/bar chart。
7. 风险页包含影响、概率、缓解措施。
8. 行动计划明确 owner / timing。
9. 创建后检查文字溢出、标题和页码。
10. 返回最终文件。

Allowed tools:
Read
Grep
Bash
PresentationCreate
PresentationEdit
PresentationRender

Model:
strong reasoning model

Effort:
high

Skill 在这里提供的是“怎么做 PPT”的方法论，而不是 PPT 文件本身。

9.7 如果用户只是找一个 PPT 文件

例如：

“看看项目目录里有没有 .pptx 文件。”

这不一定与 PPT Skill 的 whenToUse 匹配，Claude 完全可以直接：

出现“PPT”关键词 ≠ 必须调用 PPT Skill。真正依据仍是任务语义是否匹配 Skill 定义。

10. 本质上是 Hierarchical Capability Routing

                         Claude
                           │
          ┌────────────────┴────────────────┐
          │                                 │
     Atomic Tool                        SkillTool
          │                                 │
      Read/Grep                       Skill Registry
      Bash/Edit                            │
      MCP/...                         ppt-generation
                                      review-pr
                                      debugging
          │                                 │
          └────────────────┬────────────────┘
                           ▼
                    Tool Execution

可以理解成两层路由：

一级：
选普通 Tool 还是 SkillTool

二级：
如果选 SkillTool，再选哪个 Skill

这种设计避免把大量 Skill 都平铺成独立 Tool Schema，同时支持按需加载。

11. 工程面试式总结

Claude Code 中 Tool 是由统一 Tool Runtime 执行的原子能力，例如 Read、Bash、Edit 和 MCP Tool；Skill 则是以 SKILL.md 为主体的可复用过程知识、任务工作流和运行配置。Skill 本身不是普通 Tool，而是通过特殊的 SkillTool 接入 Tool Runtime。Claude 也不是通过“简单任务/复杂任务分类器”决定用 Tool 还是 Skill，而是先看到可调用 Skill 的 name、description 和 whenToUse 等轻量元数据，再由模型进行语义匹配。存在匹配 Skill 时优先调用 SkillTool，并按需加载完整 SKILL.md；没有匹配 Skill 时，模型直接组合 Read、Bash、Edit 等原子 Tool。因此 Skill 的作用不是代替 Tool，而是规定复杂任务应该按什么 SOP 组合这些 Tool。

12. 关键源码入口

  • src/Tool.ts — Tool 基础抽象。
  • src/skills/loadSkillsDir.ts — Skill / SKILL.md 加载。
  • src/tools/SkillTool/SkillTool.ts — SkillTool、inline/fork Skill。
  • src/tools/SkillTool/prompt.ts — Skill Discovery 提示与匹配规则。
  • src/commands.ts — getSkillToolCommands() 等候选集构建。
  • src/services/tools/toolExecution.ts — SkillTool 与普通 Tool 共用的 Tool Runtime。
  • src/query.ts — Agent Loop 与 Tool Runtime 主连接点。
